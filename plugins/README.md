# Wings plugins

A plugin is a folder with a `wings-plugin.json` manifest and a JavaScript file. Wings loads it into a sandboxed frame, and the plugin talks to Wings only through the `wings` object. Anything that touches your machine is checked in Rust against the permissions in the manifest.

`changes/` shows each pane's changed files as a badge and a sidebar tree, the repo's commit history, and a commit graph in a window of its own (`views`), all opening Wings' diff viewer.

`dev-servers/` puts a `localhost:<port>` badge on a pane while a program in it listens on a local port, and opens it in the browser from a button on the badge, and a `http://localhost:<port>` address in a chat's message is a link that opens it (Wings 0.2.40). It is one script with no pages, and the first plugin here written in Rust: see [Plugins written in Rust](#plugins-written-in-rust).

`worktrees/` lists the git worktrees of your projects in a sidebar, open in a pane or not, with what each one is (merged into the default branch, upstream gone, uncommitted changes, locked, folder missing, open in a pane). It removes the ones you pick, or all merged and clean ones, after you confirm, with `git worktree remove` and never `--force`, prunes records of worktrees whose folder is gone, and can delete the branch with `git branch -d`. It can also look across the whole Mac: Scan this Mac finds, with `wings.diskFind`, the repos outside your projects that have more than one worktree, and lists them under their own heading, reading them only with git commands that don't run a repo's own programs. So it doesn't check them for changes, offers no "Remove all merged" and no pane there, and warns before it removes one worktree, since `git worktree remove` can run what a repo's settings and hooks name. Needs Wings 0.1.70.

`disk/` shows what takes the space on your disks, like DaisyDisk: a disks overview, a scan of a disk or folder drawn as a map you click into, a list of what's in each folder, hidden space, and a Collector that moves what you pick to the Trash. Claude scans with its `disk__*` tools and can fill the Collector for you to review. It scans with `wings.diskUsage`, in Wings, on several threads.

`work-item/` shows the Azure Boards work item named in each pane's branch, and moves it to its next state. A work item opens as a tab with its description, comments and linked pull requests, and the work items assigned to you in the current sprint show under each Azure DevOps project in the sidebar.

`tasks/` is a lightweight issue tracker for each project, shown as Issues: a key like `WIN-12`, a type (task, bug, feature or epic), a Markdown spec (new descriptions start from a Goal, Scope, Done when and Validation template), a status (to do, in progress, in review, done, canceled), a priority (urgent, high, medium, low, shown with Linear's icons and sorted first), links (branch, pull request, commits), a parent epic or feature with progress on the epic, related and blocking issues, the Claude sessions that worked on it and an append-only activity log of who did what and when. Issue keys stay local to Wings, never in commit messages or branch names; a commit an agent makes while an issue is in progress is linked by the agent or by you with the commit, branch and PR fields. A sidebar lists the open ones, a board in a tab shows them by status, in rows by parent epic or feature like Linear's sub-grouping (each row folds and shows how many children are done), an Issue page opens as a tab (one tab reused, a middle-click or Cmd+click opens another) to read, edit, resume or start an agent on, and the open ones show under the project, children indented under their epic or feature. Claude reads and writes them with `tasks__list`, `tasks__get`, `tasks__create`, `tasks__update` and `tasks__log`, for the project of the pane it came from. Issues also answers Claude Code's hooks: at session start it tells Claude to track its work here, and a "Keep issues local" setting (on by default) denies a commit or pull request command that holds an issue key. These need Wings 0.1.54.

`schedules/` starts a coding agent (Claude Code or OpenCode) with a prompt in one of your projects by itself, every few hours or at a set time on the days you pick, and opens each run in a new tab with a notification. A timer in its main script checks what is due every 30 seconds with plain date math, so it keeps running while Wings is in the background. A run missed while Wings was closed is not made up. Claude can add one with its `add` tool and change one with `update`, but only after you allow it in an "Allow this schedule?" dialog, since it then starts agents by itself. The call waits up to 100 seconds and saves nothing if you deny it or don't answer. Its assigned entries offer a ticket to start when one is assigned to you, and Claude's `start` tool starts one the same way, but asks you in that dialog first, unless you turned on "Agents can start tickets without asking" in the entry on the Schedules page: only the page can turn it on, and `add_assigned` and `update` never do. Its Schedules page opens as a tab. It is written in Rust (see [Plugins written in Rust](#plugins-written-in-rust)), and Wings 0.2.21 or newer runs it.

`claude-chat/` (experimental, needs Wings 0.2.29) runs Claude Code as a chat in a tab instead of a terminal: `claude -p` with stream-json both ways through `wings.spawn`, its tool calls as cards and its permission prompts as Allow and Deny buttons. A new chat opens from the + menu, and the Chat badge on a Claude terminal ends that terminal and goes on with its session in a chat, started the way the terminal started it (`claude` or a wrapper like `claude-rtk`). Its tab and its header, like a terminal pane's, are named after the session, and the header's buttons go on with the session in a terminal, open the project's past sessions in a sheet like Wings' own Past sessions (search them, narrow them by time and branch, and Resume one in the chat), start a new chat, and open its page in Wings Settings: the permission mode new chats start in, Compact or Detailed output (every run of tool calls open, with each call's output), and Small, Default or Large text. Its side panel is Wings' right sidebar, the session sidebar, which follows the chat tab in front: the chat draws the sidebar's rows with its own code and sends them as JSON (`ui::export`), the sidebar draws them (`ui::import`) and hands each click back with `tellPage`'s `write`, so it runs in the chat, and the header's side panel button opens or closes it. The Changes row in its side panel opens the Changes sidebar, through an event only Wings' own plugins can send. `/usage`, `/cost` and `/context` open a dialog over the chat with the plan's limits, credits and session totals, or how the context window is spent (`get_usage`, `get_context_usage`), and a click on the side panel's Context or limit rows opens the same one. `/plugins`, `/plugin` and `/mcp` open a dialog over the chat (a `Dialog`, Wings 0.2.36) with the plugins your settings name and the MCP servers with their status, each with a checkbox: a plugin turns on or off for that chat only, in Claude Code's flag settings (`apply_flag_settings`, then Reload plugins), since `update_settings` refuses `enabledPlugins`, so the chat never writes your settings files; a server turns on or off for the project with `mcp_toggle`, as `/mcp` does. `/hooks`, `/memory` and `/permissions` (or `/allowed-tools`) open a dialog that lists what Claude Code reports: the hooks by event with what each runs for and where it is set (`get_hooks_listing`), the instruction files it loads with the tokens each takes in the context, the auto-memory folder and the memories saved there, each with a button that copies its path (`get_memory_dialog`, `get_context_usage`), and the allow, ask and deny rules with where each is set and the default mode (`list_permission_rules`, `get_settings`). The confirms name your user settings file in the folder of the account the chat runs under, which the memory dialog's user instructions path gives (`get_memory_dialog`; Claude Code's own labels say `~/.claude` whatever the account). `/clear`, `/new` and `/reset` empty the conversation and move the tab to the new session (`conversation_reset`). A compaction shows its status and a divider with the tokens before and after (`status`, `compact_boundary`), a request Claude Code retries shows in the status line (`api_retry`), and its other notes (`model_fallback`, `notification`, `informational`, `away_summary`) are short lines in the conversation. The session's name is the one Claude Code gives it (`session_title_changed`, as after `/rename`), else your first message. The chat asks for summaries of Claude's thinking as it opens (`set_max_thinking_tokens` with `thinking_display: "summarized"`, which leaves the thinking budget alone) and folds each under "Thought for 12s". Each reply and each code block has a Copy button (`copyText`). `/status` (`get_status`), `/btw <question>` (`side_question`, answered even while a turn runs) and `/export` (`export_conversation`) open a dialog that the conversation never gets; Wings lets a page copy once per click, so the export copies on the dialog's Copy button. `/plan <task>` sets the plan mode and sends the task in the same write. Claude Code's control protocol has no request that changes these, so a change runs Claude Code's own hidden command for it, which reads the edit as JSON on stdin and writes the settings file itself, under the chat's account: `claude edit-hook --json` removes a hook from your user, project or local settings, `claude edit-permission-rules --json` adds a rule to one of those files or removes one from it, and `claude edit-memory-settings --json` turns auto memory (and auto dream, when Claude Code shows it) on or off in your user settings. Hooks and rules from a plugin, your organization or the session have no button. Each change first asks in place of what it changes, with what it writes and to which file, runs on the click that confirms it, shows what Claude Code said (its warnings, or why it refused), and reads the list again a moment later, once Claude Code has seen the file change. Each of your messages has a Rewind button, which opens a dialog with Claude Code's own `/rewind` choices: Restore code and conversation, Restore conversation and Restore code. The dialog lists the files restoring the code would write back, from a dry run (`rewind_files` with `dry_run`), before you can restore them; restoring the conversation (`rewind_conversation`) drops the message and all after it and puts it back in the message box to edit and send again. A session reopened after a rewind leaves out what the rewind dropped, from the `last-prompt` line with `rewound` and `cutUuid` that Claude Code appends to its transcript. The chat has Claude Code keep the file checkpoints that needs, which `claude -p` keeps only when `CLAUDE_CODE_ENABLE_SDK_FILE_CHECKPOINTING` is set, through its flag settings as it starts. The side panel lists the background tasks that run, like a command Claude started with `run_in_background`, each with how long it has run and Stop (`stop_task`), and a click on one opens the end of what it printed in a dialog (`get_task_output`). A terminal Claude opens with Wings' `open_pane`, like a long build, shows live in the side panel (Wings hands a plugin's sidebars the terminals of its tab in front), with what it runs, whether it still runs, and buttons that open it as a tab of its own and close it; it runs on in a tab of its own once the chat closes. Words in Claude's replies that name something in Wings are links that open it there: an issue key opens the issue in Issues, a `http://localhost:<port>` address opens with Dev servers, each while that plugin is on. Both need Wings 0.2.40. A click on a subagent (its row in the side panel, Open on its call, or a background agent's name) opens its conversation in a tab of its own right after the chat's (`openView`'s `after: "self"`), named after what it is for, and a second click shows that tab again. The tab reads the subagent's transcript through Wings (`transcript`'s `agent`) and then the lines the chat passes on as the subagent prints them (`tellPage`), since only the chat's Claude Code runs it; its header stays at the top with Back to chat (`showPage`), whether it runs and for how long, its model and its chat. Its message box sends through the chat: your Enter there is handed on to the chat's page with `tellPage`'s `write`, and the chat has its Claude pass the message on with SendMessage (headless Claude Code refuses `send_task_message`), which also wakes a subagent that has finished, and notes "You messaged <subagent>: ..." in its own conversation. With the chat closed, the box says so and is off. Needs Wings 0.2.41. An update or restart of the plugin doesn't stop a chat that runs, even mid-turn: the tab's next page takes over the same Claude Code (`wings.processes`, `wings.adopt`) and shows the conversation as it was, from the session's transcript up to the first message among the lines Wings kept and from those lines on, with your answers, queued messages and the answers to its opening requests from the note the page before kept (`processNote`), which lets Wings forget the lines of each turn that ended. Needs Wings 0.2.42. Nor does a restart or update of Wings: the chat's Claude Code runs in Wings' terminal server (`spawn`'s `survive`), and the restored tab takes it over the same way. A chat never starts a second Claude Code on a session one still runs, and says so instead (Wings 0.2.47).

`pr-tracker/` is the largest plugin here, with five hosts and three pages, written in Rust (needs Wings 0.2.21). It shows the pull request for each pane's branch as a badge with live status, checks and why they failed, the diff and review comments. It lists each project's pull requests in the sidebar (yours and the ones waiting for your review, or every open one, picked on its Settings page), can send a notification (`wings.notify`) when someone opens a new one or only when one asks for your review, checked every minute while Wings is in front and at an interval set on its Settings page while it's in the background, and in a tab or a Project page block every open one with All open, Mine, Review requested and Drafts chips (the choice is kept with `setTabState` / `setBlockState`). The PR tab's Checks view lists every check or policy grouped by state, with required or optional, kind, duration, an Open link and, for a failure with a log, the end of it fetched when the row opens. It opens one as a tab to read, reply to, approve and send to an agent. A tab opened with no pull request (from its title bar button) lists the project's open ones to pick from. "View in diff" on a thread opens the viewer at its file and line. It works with GitHub (github.com and GitHub Enterprise Server hosts `gh` is signed in to), GitLab (gitlab.com and self-managed hosts `glab` is signed in to) and Azure DevOps through their CLIs, and with Bitbucket Cloud and Codeberg through an API token saved on its Settings page. Replies work on every host: in the review thread on GitHub (github.com and Enterprise), GitLab and Azure DevOps, under the comment on Bitbucket Cloud, and on Codeberg as a new comment that quotes the one it answers, since the Gitea API has no threaded replies. The Approve button (confirmed first) works on GitHub, GitLab, Bitbucket Cloud and Codeberg; Azure DevOps has a Vote menu (Approve, Approve with suggestions, Wait for author, Reject, Reset vote) that runs `az repos pr set-vote`, which finds your reviewer identity itself. Bitbucket needs the `write:pullrequest:bitbucket` token scope, Codeberg `write:issue` to reply and `write:repository` to approve.

Work item and pull request detail views reuse one tab per project. Middle-click or Cmd/Ctrl-click a project sidebar row to open another tab.

## Installing

Open Plugins (the puzzle icon in the title bar) and paste a GitHub repo link, choose a `.wings-plugin` file, or drop one on the window. The plugins in this folder that aren't installed are listed under Available, each with an Install button, and Wings shows a toast once when a new one lands on `main` (checked on start and every six hours, with the update check). A new plugin starts off. Turning it on shows what it can do and what it adds, and approves exactly that. An update that asks for more turns it off until you approve again.

From a GitHub link, Wings installs the newest release's `.wings-plugin` file, or the repo itself if there are no releases, and offers updates when a new release is out. A link to a folder in a repo of several plugins, `github.com/owner/name/plugins/<id>`, installs that folder from the default branch and offers an update when the plugin's own version there changes, so pushing a version bump ships it. An update that needs a newer Wings, by its `minWingsVersion`, isn't offered. Public repos need no sign-in. For a private repo Wings uses your `gh` sign-in, so `gh auth login` as someone who can see it. You can also share a private plugin as a `.wings-plugin` file.

An update, a linked folder read again, or turning a plugin on that is on already loads its new code where its pages show: its tabs, sidebars and windows stay open with their args and saved state, and the programs their pages run (`wings.spawn`) go on, for the page that loads in the same tab to take over (`wings.processes`, `wings.adopt`). An update that asks for more access, turning a plugin off and removing it close everything of it and stop its programs (Wings 0.2.42).

The plugins in this folder install the same way:

| Plugin | Link |
| --- | --- |
| Changes | `github.com/josippapez/Wings/plugins/changes` |
| Dev servers | `github.com/josippapez/Wings/plugins/dev-servers` |
| Disk usage | `github.com/josippapez/Wings/plugins/disk` |
| HUD | `github.com/josippapez/Wings/plugins/hud` |
| Issues | `github.com/josippapez/Wings/plugins/tasks` |
| PR tracker | `github.com/josippapez/Wings/plugins/pr-tracker` |
| Work item | `github.com/josippapez/Wings/plugins/work-item` |
| Worktrees | `github.com/josippapez/Wings/plugins/worktrees` |

From a terminal or a script, use the `wings plugin` command while Wings is open:

```sh
wings plugin install ~/Downloads/cyclops.wings-plugin   # or github.com/owner/name
wings plugin list            # --json for scripts
wings plugin link ~/code/my-plugin   # load a plugin folder in place, for development
wings plugin enable cyclops  # also update, disable, remove
```

Every plugin tool is also a command (Wings 0.1.94): `wings tools` lists them, and `wings <plugin> <tool> key=value…` runs one and prints its answer, like `wings tasks list status=todo`. A value that reads as JSON (a number, `true`, `false`, a `[list]`) goes as that, anything else as text. `--help` after a command shows its arguments.

`wings worktree-setup [project=<name|path>] [include='["a","b"]'] [setup=<command>]` (Wings 0.1.99) is Wings' own `worktree_setup` tool, which Claude also has: without `include` it prints what the project's new worktrees get (the local files copied in, a `.worktreeinclude` in the repo taking precedence, and the setup command); with it, it changes the file list, like Worktree setup in the sidebar. `include` lists patterns (`.gitignore` syntax, `!` leaves files out) and replaces the defaults, and an empty list resets it. `setup` proposes the command that runs in every new worktree before its agent starts (an empty value clears it): Wings asks you to allow it in a dialog, the call waits up to 5 minutes for your answer, and nothing is saved if you decline or don't answer. `project` defaults to the project of the pane you run in.

A plugin installed this way still waits for you to approve its access in Wings, which opens the approval. On first start Wings offers to add the `wings` command to `~/.local/bin`, and the Plugins sheet offers it later. With no arguments the command opens Wings rather than starting a second copy.

Plugins start and stop as you turn them on and off, with no restart. Installed plugins live in `<app data>/plugins/<id>/` (on macOS `~/Library/Application Support/dev.wings.app/plugins/`). Dev builds also load this repo's `plugins/` folder at startup, always on.

## Packaging

A `.wings-plugin` file is a zip of the plugin folder, with `wings-plugin.json` at its root or one folder down and the built modules in `dist/native/`. A repo that commits its modules makes one with:

```sh
git archive --format=zip --output my-plugin.wings-plugin HEAD
```

Wings installs a repo from its link too: the repo, its release's `.wings-plugin`, or a plugin folder in a repo. The modules have to be committed, because the install has no build step.

## Writing a plugin

A plugin is Rust built to WebAssembly. Wings 0.2.17 and later runs each frame (its main and each page) as a sandboxed module, with the permissions its manifest asks for. There is no JavaScript and no `src/`.

### Layout

```
my-plugin/
  wings-plugin.json     the manifest
  icon.svg
  rust/                 the crate: Cargo.toml, src/lib.rs, one file per frame
  dist/native/          the built modules, committed: main.wasm, <page>.wasm
```

- The crate is `<plugin>/rust/`, a `cdylib` that depends on `wings-plugin` (`packages/plugin-rs`). Add it to `members` in `plugins/Cargo.toml`.
- One Cargo feature per frame, named like the frame: `main`, `sidebar`, `graph`. `lib.rs` pulls in a frame's module with `#[cfg(feature = "<frame>")]`, and the module defines `#[unsafe(no_mangle)] pub fn start()`.
- The manifest names the modules: `"main": "dist/native/main.wasm"` and a page as `"page": "dist/native/sidebar.wasm"`. The frame is found by the file's name.
- A main only runs: its UI is badges, pane status, the diff viewer, project sections and its pages. A page calls `wings_plugin::run(view)` (or `run_filled` for a page that fills its tab edge to edge) in `start`. `view` returns the page's nodes from the page's state. It runs again after every turn (an event, an answer, a timer), and the app gets the tree when it changed.

### Build and check

```sh
rustup target add wasm32-unknown-unknown   # once
sh build-rust.sh                           # every plugin; `sh build-rust.sh <plugin>` for one
sh build-rust.sh --check                   # fails when a committed module differs from what rust/ builds
pnpm test                                  # cargo test --workspace: the plugins' own tests
```

Run `sh build-rust.sh` from `plugins/` and commit the `.wasm` files with the source. Debug builds of the app load this repo's `plugins/` folder at startup, always on (`cargo run --manifest-path apps/native/Cargo.toml -- --plugins-dev-root plugins`), and a release app takes `wings plugin link <folder>`.

### Building a page

`wings_plugin::ui` has the components, by the names and props the app reads: `page`, `toolbar`, `row`, `stack`, `card`, `list`, `list_row`, `button`, `text`, `muted`, `title`, `heading`, `badge`, `chips`, `select`, `checkbox`, `text_input`, `search_field`, `combobox`, `gauge`, `graph`, `empty`, `loading`, `notice`, `confirm`, `dialog`, `sheet`, `icon` and more. Anything else is `Node::new("<kind>")` with `.prop`, `.on` and `.child`. A `Scroll` with `follow: "end"` stays at its end as what it holds grows, while you haven't scrolled up, as a chat does (Wings 0.2.29). Give that `Scroll` an `onReachStart` handler and Wings sends it (no payload) when the scroll comes within a screen of its top, once until what is above it grows; the page then puts older items at the top and Wings keeps the view on what it showed, so a long chat loads older messages as you scroll up. Leave the handler off when there is nothing older to add (Wings 0.2.36). A `Textarea` with `submitOnEnter: true` sends Enter to its `onKeyDown` and starts a new line on Shift-Enter (Wings 0.2.29). A `Textarea` with `takesTab: true` sends Tab to its `onKeyDown` (`key: "Tab"`) in place of moving focus on, so a page can complete from it; Shift-Tab still moves focus back, and a page sets it only while it has something to complete, so Tab leaves the field the rest of the time (Wings 0.2.36). A `Textarea` with `takesShiftTab: true` sends Shift-Tab to its `onKeyDown` (`key: "Tab"`, `shiftKey: true`) in place of moving focus back, and one with `historyKeys: true` sends Up from its first line and Down from its last (`key: "ArrowUp"`, `"ArrowDown"`) in place of moving the caret to the start or the end of the text, so a page can recall earlier messages; a Textarea's Escape reaches `onKeyDown` as a key of yours, so the page may write to a program it runs (Needs Wings 0.2.40). A `Textarea`'s `placeholder` may change from one build to the next. A one-line `TextInput` with an `onKeyDown` handler hears Enter and Escape from it (`key`), and Enter carries `shiftKey: true` when Shift was held, so a search field can go to the previous match on Shift-Enter (`shiftKey` needs a Wings after 0.2.60; an older one sends none, which reads as Enter). A `Textarea` with an `onPasteImage` handler gets `{ "mediaType": "image/png", "data": "<base64>" }` when the user pastes an image (png, jpeg, gif or webp, up to 3.75 MB, so its base64 stays under 5 MB), and as with a key the page may then copy or send; text pastes are unchanged, and without the handler an image paste does nothing (Wings 0.2.35). Wings 0.2.30 adds, for a chat: a `Stack` with `enter: "rise"` fades and lifts each child in the first time it shows; a `Text` with `shimmer: true` pulses, for something under way like "Thinking"; a `Select` with `variant: "ghost"` is as wide as its choice with no box; a `Textarea` with `variant: "bare"` has no frame, for a field inside a `Card` with `variant: "raised"`, which is rounder and lifted by a shadow. Wings 0.2.31: a `Text` with `since` (milliseconds since the epoch) ends with how long ago that was and counts it up, as in "Running pnpm test · 16s", so the page doesn't send a new tree each second. Wings 0.2.36: a `Split` (a `start` and an `end` slot, `defaultSize` points wide for the fixed one, 280 by default) takes `side: "end"`, which makes `end` the fixed pane, on the right, with no border, 12 points of padding and its own scroll, for floating cards, while `start` takes the rest and doesn't scroll, so it can hold a page that scrolls itself; `collapseBelow: <points>` leaves the fixed pane out while the split itself is narrower than that, so a narrow tab keeps the main pane at full width (the app measures the split as it draws, so the pane follows a resize a frame late); and `pinned: true` shows the fixed pane whatever the width. A fixed pane with nothing in it isn't drawn. A `Scroll` with `textScale` (a number from 0.5 to 2, 1 by default) multiplies the size of every text inside it, by each text's `size`, so a page can offer a text size setting; a `Scroll` inside one without its own `textScale` keeps the scale (Wings 0.2.36). Also in 0.2.36: a `Button` with `round: true` is fully rounded, a circle at the `icon` sizes, like a chat's send button; and the menu of a `Select` with `variant: "ghost"` is as wide as its longest option (up to 360 points), not as narrow as the choice it shows. A page sends at most 5,000 nodes: `Node::count` says how many a node makes, so a long list can show its newest that fit. A `Menu` is a button that opens a list of actions over the page: its first child is that button (with no `onClick`, as the app opens the menu), and each child after it a `Button` with its `onClick`, red when its `variant` is `destructive`. `align: "end"` lines the menu up with the button's right edge. Give a row of a list a `key`, so it keeps its state between builds. A button or a text takes a `title` prop that the app shows as a tooltip on hover (`.prop("title", "...")`), and so does a `ListButton` (Wings 0.2.36). A `Button` or `ListButton` with `shortcut` (`.shortcut("cmd-shift-p")`: Cmd or Ctrl, maybe Alt and Shift, and a letter, a digit, a punctuation key or F1 to F12) is clicked by that key while its page's tab has the keyboard, and shows it in its tooltip beside its `title` or label, as the app's own header buttons do; while a `Dialog` shows, only the dialog's buttons answer. Wings drops a shortcut it or a text field already has (Cmd-Q, Cmd-W, Cmd-T, Cmd-N, Cmd-comma, Cmd-1 to 9, the font keys, Cmd-A, Cmd-Z...) and Ctrl-Shift without Cmd, which are its keys off macOS. A `Page` with an `onTextScale` handler (`.on_text_scale(|step| ...)`) sizes its own text: while its tab has the keyboard, Cmd-+, Cmd-- and Cmd-0 send it `{ "step": "bigger" | "smaller" | "reset" }` in place of changing the terminals' font (Needs Wings 0.2.54). A `Page` with `backdrop: "pixels"` (`.backdrop("pixels")`) has Wings draw a slow drift of dim, dithered pixels in the page's colours behind the whole page in place of its plain ground, where the page fills a tab; it moves only while the window is in front, stands still under Reduce motion, and a step of it never builds or draws the page again. Elsewhere, and in an older Wings, the page keeps its plain ground (Needs Wings 0.2.59). `backdrop: "gradient:<preset>"` has Wings draw a slow moving gradient there instead, with a Metal shader of its own, in the colours of one of ShaderGradient's presets (`halo`, `pensive`, `mint`, `interstella`, `nighty-night`), dimmed so the page's muted text keeps 4.5:1 on every pixel; it steps as the pixels do, and where Metal can't be set up it is the plain ground (Needs Wings 0.2.60). `backdrop: "pixels:<pattern>"` is another pattern of the pixels: `rain` (drops of the blue falling down small cells), `checker` (a coarse checker with a faint band of light sweeping across it) or `embers` (sparks of the Claude orange rising over a dim warm glow), in the same few shades near the ground; a pattern Wings doesn't know is the drift, and a Wings before it knew any (0.2.60 and older) keeps the plain ground (Needs a Wings after 0.2.60). In the app's window both are drawn in a layer under the window, so a step of one draws nothing of the window at all. A `Dialog` (`ui::dialog(title, width, on_close)`, Wings 0.2.36) is a dialog over the page, drawn as Wings' own are wherever the page puts it in its tree: a dimmed backdrop over the whole page and a panel `width` points wide at most (560 by default, from 280 to 1,000), with its `title`, a close button and its children under them, which scroll. It takes the keyboard while it shows, and Tab stays in it. Escape, a press on the backdrop and the close button send its `onClose` (no payload; the press and the button count as a click for `copyText` and `processWrite`, Escape doesn't), and the page then leaves it out, which gives the keyboard back to what had it. Unlike a `modal` view it is part of the page, so it reads and changes the page's own state. Wings 0.2.37 adds a `Sheet` (`ui::sheet`): a panel 480 points wide that slides in over what holds it from the right edge, drawn as Wings' own Past sessions sheet, with a `title` and a `description` slot at its top and a close button, a `header` slot under them over a hairline, and its other children under that, scrolling; put it last in the page's body, so it covers the page. Its `onClose` hears Escape, a press on the dimmed page beside it and its close button (the press and the button count as a click for `copyText` and `processWrite`, Escape doesn't), and the page then leaves it out. A `SearchField` in its `header` is the sheet's search, Wings' search box with its icon, which has the keyboard while the sheet shows (the keyboard goes back where it was once the sheet is gone), and `Chips` there are drawn as the sheet's toggle. Also in 0.2.37: a `Bar` with `variant: "slim"` is as tall as a terminal pane's header, for a title and a row of `icon-sm` buttons; a `Text` inside a line of text takes `mark: true` for a word a search found, marked as Past sessions marks it; and an `Icon` takes a `size` in points (16 by default) and the name `claude`, the Claude spark in its own orange. Wings 0.2.40 adds, for a page that runs an agent: a `Terminal` (`pane`, the id of a terminal its agent opened, and `height` in points, 220 by default, from 80 to 800) draws that terminal live where it sits, with a header that says what it was opened to run and whether it still runs, and buttons that open it as a tab of its own and close it. Wings draws it over the page, so what it prints never builds the page again, and draws only a terminal the agent of the page's own tab opened (see `ui` `terminals` and `wings.onTerminals`): any other `pane` is a line saying so. It isn't drawn while the page shows a `Dialog` or a `Sheet`. And a `Text` with `links: true`, or every `Text` in a `Stack` with `links: true`, shows the words a plugin that is on declares in `contributes.links` as links: a click opens that plugin's view, or the address, and the page never hears of it. Wings finds them once for each text, not each time the page draws. An `Image` (`ui::image`, Needs Wings 0.2.40) shows a picture the page registered with `wings.registerImage`, named by `src`, which is only that id: a path, a URL or anything else is left out, so a page can't read a file or fetch one through it. It takes `maxWidth` and `maxHeight` in points (240 by 180 by default, up to 2000): the picture is scaled down to fit and never up, or with `fit: "cover"` fills the whole box and is cropped. `radius` rounds its corners (6 by default, up to 24), `label` is what a screen reader says, `fitWindow: true` also keeps it within the window less a dialog's frame (for one shown large in a `Dialog`), and `onClick` hears a click. Wings decodes a picture once, off the page's thread, only when a page shows it and at the size it is drawn (so a screenshot costs a thumbnail's memory in a list and its own size in a dialog, never more than 1600 pixels on its longest side), and the same bytes registered twice are one picture; until it is ready the node is a quiet box of the picture's size, so the page doesn't move. A `Split` with `side: "end"` and `float: true` floats its `end` pane over the right edge of the split as tall as what it holds, so `start` keeps the whole width and never moves for it; the page decides when the pane shows by what it puts in the `end` slot (Needs Wings 0.2.41). Its `onNarrow` handler hears `{ "narrow": true | false }` when the split's width crosses `collapseBelow`, and once when it first has a width, so the page knows whether there is room for the pane beside its content; a floating pane is never left out by `collapseBelow` or `pinned`. A floating `Split` with an `onClose` handler has the pane open over the content: it takes the keyboard, and Escape in it and a press anywhere outside it send `onClose` (no payload), after which the page leaves `onClose` and the pane out. A `Terminal` inside it is drawn over the pane where it sits, and goes with it when the page leaves the pane out. A `Scroll` whose only child is a `Stack` (its column) takes `scrollTo: { index, token }` (Needs Wings 0.2.42): it scrolls so the `index`th child of that column is at the top of the view, once for each new `token`, so a page keeps sending the same pair until it wants another jump (a repeated token does nothing, and an `index` the column doesn't have yet waits). It also takes `track: [index, ...]` (ascending) with an `onTrack` handler: Wings tells the page `{ at }`, the position in `track` of the last child whose top is at or above the top of the view (`null` when the view is above all of them), once when the scroll is laid out and then whenever that changes, so a page can show where in a long conversation the reader is without hearing about each scroll step. Both work with or without `follow: "end"`. A `Split`'s `defaultSize` may be as small as 16 points (Needs Wings 0.2.42; it was 120), for a slim rail. `PromptRail` (Needs Wings 0.2.44) is the slim rail of a chat's prompts: a column of short ticks, one for each entry of `marks: [{ title, preview }]` (a title is cut to 200 characters, a preview to 400, and 2,000 marks are kept), left-aligned and 20 points apart, closer down to 12 and then the rail scrolls (6 before Wings 0.2.49). The tick of `current` (an index into `marks`) is long and bright and its neighbours step down in length; the pointer does the same to the tick it is on and shows a card beside it with the title over the start of the preview. Wings draws all of that itself, so hovering never reaches the page. A click on a tick or the card sends `onSelect` with `{ index }`. Give it a slot about 64 points wide and a height of its own, as a `Split`'s `start` slot gives it; `plugins/claude-chat/rust/src/rail.rs` is the one to copy from. A page may write to a program without a click only lines that are Claude Code control requests to draw (`ui_attach`, `ui_render`, `ui_panes`), so a chat can redraw a Claude Code plugin's pane when it changes (Needs Wings 0.2.51). A `HoverCard` shows its `card` slot as a card under what else it holds while the pointer is on either, drawn by Wings so hovering never reaches the page; `width` sets the card's width in points (300 by default, 160 to 480) (Needs Wings 0.2.50). A `Stack` with an `onContextMenu` handler hears a press of the right mouse button inside it as `{ "x", "y" (window points), "child" (the index of the stack's child under the pointer, or `null`), "code" (`{ "text", "isBlock": true }`, when the press was on a `Code` node), "link" (`{ "href", "text" }`, when it was on a `Text` link inside a line that has an `https:` `href` prop, as `markdown` makes) }` and nothing outside it hears that press; a `PopupMenu` takes `x` and `y` (window points, where it opens, moved in to stay in the window), an `onClose` handler (sent on Escape and on a press outside it, after which the page leaves the menu out) and `Button` children, each with `onClick` (a click for `copyText` and `processWrite`; the page then leaves the menu out), its text or `label`, an optional `description` drawn dim under it, and optional `disabled` (Needs Wings 0.2.52). Wings lets the user select words of a `Text` by dragging (a double press takes a word) and copy them with Cmd-C, and a right-click in a `Stack` with `onContextMenu` while words are selected also sends `"selection": { "text" }`, the selected words, so a menu row can act on them (Needs Wings 0.2.52). `ui::palette(Some(colors))` paints the page in its own colours in place of the app's from its next render, as a Claude Code mod's theme does the chat: `base` (under a floating pane), `page`, `dialog`, `popover`, `text`, `muted`, `info`, `danger`, `done` and `working`, each `#rrggbb`, and `ground`, what the page lies on, `{ "from", "to", "angle" }` (degrees, as in CSS). A role left out, or one that isn't a colour, keeps the app's, and `None` gives the app's back. Text fields keep the app's colours (Needs Wings 0.2.52). A `Stack` with `fill: true` takes what is left of its parent's height and no more, so a `Scroll` in it scrolls while what follows it stays in view, and a `PromptRail` with `beside` in it is as tall as that stack (Needs Wings 0.2.49). A `Code` node (`markdown::highlighted_code(code, language)` in the SDK) draws `code`, the lines of a code block, as one text in a card: Wings colours it with the diff viewer's highlighter when `language` is a name it has a grammar for, a Markdown fence's (`rust`, `typescript`, `bash`) or a file's extension (`ts`, `py`), and draws it plain otherwise. It is one node however many lines it holds, and the colouring runs on a thread of its own and is kept by the code, so a page that builds again with the same text, or a block that grows a token at a time as a reply streams, never waits on it: the lines the last colouring still matches keep their colours and the rest are plain until the new ones arrive. It keeps up to 400,000 characters, and a block the page folds sends only the lines it shows. `tone: "success"` or `"danger"` makes it a tinted band with a bar in that colour instead of a card, for the added or removed lines of a diff. Needs Wings 0.2.45; an older Wings leaves the node out, so set `minWingsVersion` to match. `plugins/changes/rust/src/sidebar.rs` is a page to copy from.

For a list, a group of rows or a dialog's buttons, name what it is and let Wings lay it out, instead of building it from `stack`, `row` and `text`: pages that built these by hand each came out a little different (a heading a few points left of its rows, a row's text at another x when it had no icon, Cancel after the button it cancels, or in another variant). The page's own state lives in a `thread_local!` that handlers and tasks change. `wings_plugin::task::spawn` runs an async task (a `host::exec`, a `cli` call) and the page is built again when it has made progress. Lines a program prints (`host::spawn`, `host::exec_lines`) build the page at most 30 times a second, however fast they come.

### Talking to main

Main and each page are separate frames, and they talk through messages (`messages::tell` and `messages::on`, JSON of at most 64,000 characters, to the other frames of the plugin). Don't write request ids or timeouts by hand. A page tells main what it wants (`open`, `commit`) with an `id`, and main tells back `{ id, error }` under a `done` message, as `changes/rust/src/lib.rs` does. `ipc.rs` of `pr-tracker` sends long messages in parts. A value every frame reads and hears change is a `settings::Setting`. What a plugin keeps is `host` storage, which every frame shares.

### Tools

Claude's tools, which are also `wings <plugin> <tool>` commands, are declared in the manifest's `contributes.mcpTools` (name, description, input schema) and answered in main with `tools::register(name, schema, run)`. The input is checked against the schema before `run`, so a wrong one comes back to Claude as an error that names the field. A schema with a `pattern` can't be registered: register it without the pattern and check the field by hand. Claude sees only the tool names and the `mcpInstructions` line (up to 500 characters) at the start of a session.

### Tests

- The plugin's own tests run with `cargo test` (`pnpm test`). Built for this computer, the SDK has no host: nothing is drawn or sent, a call is never answered, the clock stands at 0 and the zone is UTC. `host::testing::answer` answers the plugin's calls with made-up output, `host::testing::set_now` moves the clock and `local_time::testing::zone` sets a zone.
- `apps/native/src/page/plugin/shipped.rs` runs the committed modules against a fake app and the manifest they declare, so a call a plugin makes meets the permission its manifest grants. It rebuilds nothing: run `sh build-rust.sh` first.
- The app's own tests use Rust fakes (`src/page/runtime/fake.rs`) or a real module built from `apps/native/pages/fixture-wasm*`.

### Screenshots

A page is looked at before it ships. `apps/native/examples/shot_plugins.rs` renders plugins offscreen with real rendering, over made-up data, at 1000 and 640 points wide, and prints each PNG's path. macOS only. The first run after a module changes compiles it, and a page that takes over 10 seconds to show fails with `page did not show ...`: run it again.

```sh
pnpm --dir plugins shot <out-dir> --changes
# the same: cargo run --manifest-path apps/native/Cargo.toml --example shot_plugins --features test-support -- <out-dir> --changes
```

The flags are `--changes`, `--schedules`, `--hud`, `--disk`, `--work-item`, `--tasks`, `--pr-tracker` and `--stopped`. With no flag it renders Worktrees' sidebar over a repo it makes. `--external <folder>` renders the plugins shipped from their own repos. `--tooltips` points at a titled Button and Text until their tooltips show. A new plugin or page gets a scene in `shot_plugins.rs` that builds the committed module over made-up data: copy the one for the plugin nearest to it.

`dev-servers/` is the smallest one to read, and `hud/` has a main script and a page: a crate with two frames, unit tests that run with `cargo test` (`pnpm test` runs them), and `apps/native/examples/shot_plugins.rs --hud` to render its sidebar. `changes/` has three frames and the diff viewer: its pages run git themselves and ask its main to open a diff. `worktrees/` is a page that runs git and searches the disks. Its tests answer the plugin's calls with a made-up git (`host::testing::answer`), and `shot_plugins.rs` with no flag renders it over a repo it makes. `work-item/` is the one that runs `az`: its main badges panes and fills each project's Work items section, and its item tab (it reads what it was opened with by `host::view_args`, so it needs Wings 0.2.21) and Sprint block run `az` themselves. The SDK has what it needed: `cli::Cli` runs `az`, `gh` or `glab` and tells a missing program and a signed-out one from a failure (with the badge for either, Sign in and Try again), `azure::parse_remote` and `azure::work_items` (the work items asked together are one `az rest`), `cache::Cached` (a value per key, with a TTL and a TTL for a failure) and `cache::Batch`, `git::watched_project`, `host::open_view_with`, `host::set_project_section`, `host::block_state`, and `run_filled` for a page that fills its tab edge to edge. Its tests in `shipped.rs` run in a process of their own where `az` is a fake script, which answers from `apps/native/examples/shot_plugins/work_item_az.json`, so no test reaches Azure DevOps even when the Mac has `az` installed. `schedules/` has a main that keeps the timers and makes every change, and two pages (the Schedules tab and the "Allow this schedule?" modal) that read what main saved themselves and ask it for a change with `messages::tell`, which it answers with a `done` message. It needed `local_time` (the Mac's wall clock as JS `Date` has it, through a change to summer time; `local_time::testing::zone` sets a zone for a test), `remote::parse_remote` (the forge a git remote names: Azure DevOps, GitHub or GitLab) and `host::exec_lines` (`wings.exec` with `onOutput`, for a login that prints a code). A tool whose manifest schema has a `pattern` can't register that schema, so Schedules registers it without the pattern and checks `time` by hand. `tasks/` (Issues) has a main and four pages, and answers Claude Code's hooks with `wings_plugin::hooks::on_hook`, which needs `tools::register` called in the same main, since the host sends a hook to the same message a tool call comes in; its pages read the issues from storage and ask its main to change them with a message and an answer.

`disk/` is the one that scans disks. Its main runs every scan with `host::disk_usage` (which streams the scan's progress and has a `stopper`) and keeps the Collector, and tells its tab what describes each scan over the plugin's messages (`ask.rs` is a tab's ask-and-wait over them), never a tree: Wings keeps the trees of the scans it ran for `reuse`, so the tab asks for the folder in the middle of its map down six rings, and a tool for the folder it answers about, with `wings.diskUsage` and `reuse: true`, a few thousand entries at most. A scan's own answer asks for one entry. Its tests need no disk: `cargo test` runs them, and its page is rendered over a folder of made-up files by `shot_plugins.rs --disk`.

`pr-tracker/` has four frames: its main badges the panes and fills each project's Pull requests section, opens the diff viewer and posts the replies typed in it, and answers `failing_checks` and `pull_request` (the PR for the branch of a folder, which Claude chat's side panel reads with `callTool`, as a chat is no pane); the PR tab, the Pull requests block and the Settings page run `gh`, `glab`, `az` and the API calls themselves (`forges/` has one module per provider), and ask main (`ipc.rs`: messages, in parts when long) for what only it can do or already holds: the lists the sidebar loads, the diff viewer, the agent on a branch. A poll costs few processes: panes on one repo and branch share one lookup, and the lists of every project are one GraphQL call on GitHub (`track/budget.rs` counts them). It added to the SDK: `remote::parse_remote` (which forge a remote URL is), `github::github_pulls` (one `gh` call for many repos), `settings::Setting` (a value every frame hears change), `Cli::exec`, `Cli::post` and `Cli::sign_in_with` (the login's output, for gh's one-time code), `host::exec_stream`, `diff::open_live_id`, `cache::Cached::peek`, `format::iso_of` and `host::testing::set_now`. Its tests in `shipped.rs` run in a process where `gh` and `az` are fake scripts that answer from `apps/native/examples/shot_plugins/pr_tracker_gh.json` and `pr_tracker_az.json`.

## Manifest

```json
{
  "id": "pr-tracker",
  "name": "PR tracker",
  "version": "0.1.0",
  "description": "Shows the pull request for each pane's branch.",
  "api": 1,
  "main": "dist/main.js",
  "permissions": {
    "exec": [
      "git branch --show-current [--show-current]",
      "gh pr list [--head --state --json]",
      "gh pr view [--json]"
    ],
    "transcript": [
      "pr-link"
    ],
    "openUrl": [
      "https://github.com/"
    ]
  },
  "contributes": {
    "ui": [
      "badges",
      "diff"
    ]
  }
}
```

| Permission | Allows |
|---|---|
| `exec` | Running these commands, with no shell and no stdin, 30 s timeout by default. Each entry is a program and the subcommand the arguments must start with, so `gh pr view` allows `gh pr view <url> --json title`. A bare program name allows any arguments. An entry can end with the only flags it allows, like `az boards work-item update [--id --state]`, which refuses `--title` or any other flag. Only flag names are listed; their values, and arguments that don't start with `-`, stay free. A flag in the command itself is listed too, like `git branch --show-current [--show-current]`. `[]` allows no flags at all, like `git remote get-url []` (Wings 0.1.108; older Wings refuse the plugin, so set `"minWingsVersion": "0.1.108"`). Give every entry a list: one without lets the plugin pass any flag Wings doesn't refuse outright, so list exactly the flags its calls pass, including the ones a helper adds, like `-o json` and `--organization` that `cli::Cli` callers pass |
| `processes` | Keeping these programs running and talking to them with `wings.spawn`, like an agent run headless (`claude [-p --input-format --output-format --verbose]`). Entries are written and matched like `exec`'s, and `exec`'s argument checks apply. Past the words its entry names, a program gets only flags, each value joined to its flag (`--resume=<id>`): a loose word could be read as a subcommand, like `claude mcp add`. Listing a command under `exec` doesn't allow it here. Needs Wings 0.2.29 |
| `post` | POSTing to these API paths through a signed-in CLI with `wings.post`. Each entry is `gh`, `glab` or `az` and a path where `*` stands for one segment, like `gh repos/*/*/pulls/*/comments/*/replies`. `az` paths are full `https://` URLs. An entry may end with ` {field=a\|b}`, which pins that body field to one of those values, like `gh repos/*/*/pulls/*/reviews {event=APPROVE}` (an approval that can't be turned into a "request changes"); a request whose field has another value, or none, is refused. A `gh` or `glab` entry is a plain path, with no query, `=` or empty or `.` segment, and a post whose path ends in `graphql` may only read: a `mutation` or `subscription` is refused. `exec` refuses the write flags of `gh api` and `glab api` |
| `transcript` | Reading these Claude Code transcript entry types. `attachment:<kind>`, like `attachment:model`, allows one kind of attachment entry: attachments include whole files and hook output, so ask for the kinds you need rather than `attachment` |
| `openUrl` | Opening URLs that start with these prefixes: `https://` for any page, an https prefix whose host ends with `/` like `https://dev.azure.com/`, or http to this computer only (`localhost`, `127.0.0.1`, `[::1]`, without credentials) with a port or path next, like `http://localhost:`. Any other entry is refused when the plugin loads, since `https://dev.azure.com` would also match `https://dev.azure.com.example.com/` |
| `fetch` | Calling https URLs through `wings.fetch`. A bare entry is a prefix for any method, like an API's base URL ending in `/`. `GET <prefix>` allows only GET and HEAD. `POST <url>` allows one write: `*` stands for one path segment, there is no query, and the body must be a JSON object (or absent, when nothing is pinned) up to 64 KB, like `POST https://api.example.com/2.0/repos/*/*/pulls/*/comments`. A POST entry may end with ` {field=a\|b}` to pin body fields, like `POST https://codeberg.org/api/v1/repos/*/*/pulls/*/reviews {event=APPROVED}`. Wings refuses `PUT`, `PATCH` and `DELETE` on a `GET` or `POST` entry. Needs Wings 0.1.27. `id` is lowercase letters, digits and dashes. `api` must be `1`. A `page` is a built file, like `dist/sidebar.html`: the build fails on one it doesn't write and the folder doesn't have.

A command runs as you, with that CLI's own sign-in, so `gh api` can read anything your GitHub account can. Only declare commands you need, because that list is what the user approves. A command runs in its `cwd`, which has to be a folder inside one of your Wings projects once `..` and symlinks are resolved, or inside a git repo one of your open panes is in (a built-in plugin may also run `git worktree list` in any repo); git needs one, and any other program without one runs in `/`. On top of the manifest, Wings refuses, whatever it says:

- an option before a `git`, `gh`, `glab` or `az` command, like `git -C . config`, and the commands that change a CLI's own settings: `git config`, `gh config`, `gh alias`, `gh extension`, `glab config`, `glab alias`, `az config`, `az configure`, `az cloud`, `az extension` and `az devops configure`;
- flags that run other commands, touch files, change data on the server or print a token: `git -c`, `--upload-pack`, `--output`, `--no-index`, `gh`/`glab` `-X`, `--method`, `-f`, `-F`, `--input`, `--form`, `--show-token`, and for `az` `--method`, `--http-method`, the file flags (`--in-file`, `--out-file`, `--output-file`, `--file`, `--destination`, `--source` and their short forms) and `@path` values, which az reads as files;
- a git path that leads outside `cwd`: one with `..`, or one whose file or folder, symlinks resolved, is elsewhere, since `git diff <a> <b>` compares any two files once one is outside the repo, or anywhere outside a repo. A path that names nothing on disk, like a revision, is fine. Also a `git fetch` refspec with a destination or `+`;
- a `gh api` or `glab api` endpoint that isn't a plain path like `projects/g%2Fp/merge_requests?per_page=100` (glab sends its token to any host a full URL names), and `env` or `$ENV` in gh's `--jq`;
- an `az` call that reaches anything but Azure DevOps: `--organization` must be a `dev.azure.com` or `<org>.visualstudio.com` organization and `az rest --url` an Azure DevOps URL. `az account get-access-token` takes only `--resource 499b84ac-1321-427f-aa17-267ca6975798` and `-o`, `az login` only `--allow-no-subscriptions` and `-o`, `gh auth login` only `--web`, `--clipboard` and `--hostname`, and `glab auth login` only `--web` and `--hostname`.

git also ignores a bare repo it finds in a command's folder (`safe.bareRepository=explicit`), and a package with a `.git` folder or file isn't installed. That still can't cover every subcommand of every CLI, so treat an `exec` entry as trusting the plugin with that command.

A `panes` command is typed into the new pane's shell, the way Wings resumes a session, so you're back at a prompt when it exits. It runs as you in a terminal you can see, the same trust as `exec`, and the same checks run on everything typed after the program, `args` included. A `\` in a value is written outside its quotes, so fish reads it like the other shells. Since a shell reads it, every word of an entry and of a command may only use letters, digits and `-_./:=@%+,`: no spaces inside a word, quotes, `$`, globs or operators. Words past the declared entry come from the plugin and are single-quoted. A `cwd` has to be a folder inside one of your Wings projects once `..` and symlinks are resolved, so neither can lead out of it.

Plugins don't load on Windows yet. WebView2 gives child frames the app's IPC bridge, so each plugin needs its own webview there first.

### Badges

A badge is `{ label, tone, icon?, counts?, loading?, title?, subtitle?, rows?, actions? }`:

- `tone` is one of `neutral`, `info`, `success`, `warning`, `danger`, `merged`.
- `icon` is one of `pr-open`, `pr-merged`, `pr-closed`, `pr-draft`.
- `counts` are `{ icon, value }` chips after the label, where `icon` is `changed`, `push` or `pull`. Leave out zeros.
- `rows` are `{ label, value, tone? }`, shown in the card when you click the badge.
- `actions` are `{ id, label, primary? }` buttons in that card. A click calls `onAction`.
- `loading: true` shows a spinner in the pill while the plugin refreshes.

A review comment is `{ id, replyTo, path, line, side, author, body, createdAt, url, canReply }`, where `side` is `additions` or `deletions`, and `canReply` on a thread's first comment shows a reply box under it. `path` is `null` for a comment on the whole pull request, and `line` is `null` for comments on code that has changed since. Both show under Discussion in the viewer.

Wings keeps the books for badges, statuses and project sections, so a plugin keeps no copy of what it sent. A frame skips a `setBadge`, `setPaneStatus`, `setPaneRail` or `setProjectSection` that repeats what it sent last for the same pane or section, `null` included (Wings 0.1.17 and newer for badges and statuses, 0.1.50 for sections), and Wings keeps the same badge object for an identical one and ignores section rows that are identical to what the section already shows, so setting the same thing again costs nothing. So set them on every pass, with no signature map and no list of what is shown. Wings drops the badges, statuses and rails of a pane when it closes, so a plugin needs no cleanup for closed panes, and a `setBadge` for a pane that is gone rejects with `no pane <id>`. Send `null` only to clear the badge of a pane that stays open, like a pull request that was merged.

### Pane status

A status is a slim strip under a pane's terminal, for figures you want in view all the time, like usage. A badge is something to act on; a status is something to glance at. The strip shows only while at least one plugin has set a status for the pane, and its height stays fixed while the items update.

```js
await wings.setPaneStatus(paneId, {
  items: [
    { label: "5h", value: "8% · 4h19m", percent: 8, tone: "success" },
    { label: "ctx", value: "62%", percent: 62, tone: "warning" },
  ],
  rows: [{ label: "Model", value: "Opus" }],
  open: "hud",
});
```

- `items` are 1 to 4 figures, left to right: `label` (muted, up to 16 characters), `value` (up to 32), `percent` (0 to 100, draws a small meter) and `tone`, which colours the meter and the value.
- `rows` are up to 12 `{ label, value, tone? }` lines in the card shown when you point at the strip.
- `open` is the id of one of the plugin's sidebars or views. Clicking the strip opens it, in the first place its `opens` lists.
- One status per plugin per pane; `null` removes it. With several plugins, each plugin's items sit in plugin order, separated by a dot.
- Wings rejects a call that breaks a limit, with the reason, instead of cutting the text like a badge does. Sending what the frame sent last does nothing, so you can call it on every poll.
- Wings drops a status when its pane closes or the plugin stops. When several plugins add to the same place, the extra pane badges fold into a "+N" button and title bar buttons past the first three into a menu.

### Pane rail

A rail is a small card floating over a pane's terminal, for a list you want in view while the agent works, like its todo list. A status is a strip of figures; a rail is a list of steps. Needs Wings 0.1.54 and `"rail"` in `contributes.ui`.

```js
await wings.setPaneRail(paneId, {
  title: "Todo",
  items: [
    { text: "Read the hook docs", status: "done" },
    { text: "Draw the rail", status: "in_progress" },
    { text: "Write the docs", status: "pending" },
  ],
  open: "board",
});
```

- `title` is up to 40 characters. `items` are up to 30 `{ text, status }` lines, `text` up to 200 characters and `status` one of `pending`, `in_progress` (highlighted) or `done` (dimmed and struck through).
- `open` is the id of one of the plugin's sidebars or views. Clicking the title opens it, as with a pane status.
- The card starts in the top right. The user drags its header to move it, and it snaps to the nearest corner; minimises it to a pill that shows the title and `done/total`; and closes it, which hides it for that pane until the plugin sends a different rail, so a new step brings it back. The corner and the minimised state are one setting for every pane, and the card stays inside the pane when it resizes.
- It is drawn by Wings over the terminal and never takes its keyboard focus. Moving it doesn't resize the terminal.
- One rail per plugin per pane; `null` removes it. Rails of several plugins stack in the same corner, in plugin order.
- Wings rejects a call that breaks a limit, with the reason. Sending what the frame sent last does nothing, so you can call it on every poll. Wings drops a rail when its pane closes or the plugin stops.

Plugin tools reach Claude through one MCP server, `wings`, which you add once from the Plugins sheet with Connect. It runs `wings --mcp` at user scope, so every Claude Code session gets the tools of the plugins that are on, and the list updates as you turn plugins on and off. The tools only work while Wings is open.

Wings adds tools of its own to that server, with or without plugins:

| Tool | What it does |
| --- | --- |
| `search_history`, `read_session` | Find and read past Claude Code and OpenCode sessions. |
| `list_sessions` | The open panes: id, project, folder, program and, for Claude, its state (working, blocked, done or idle), what it waits for, session id and name. Under `tabs`, the agents tab pages run (`wings.setAgent`), like Claude chat's: tab id, project, plugin, state, summary, session id, name and account. |
| `send_to_agent(pane_id, message)` | Puts a message in another agent's prompt, a pane's or a chat tab's (by its tab id), with a first line naming the sender. Sent only while "Let agents message each other" is on; the reply then has a `waitCommand` that ends with the agent's turn. A tab page hears it with `onAgentMessage` (Wings 0.2.54). |
| `read_pane(pane_id, lines?)` | The last up to 200 lines (32 KB) of a pane's output as plain text. Marked as data, since a pane can print anything. |
| `open_pane(cwd?, command?, run?)` | A new tab with a command typed in it. A `cwd` inside a project you added opens in that project; any other folder opens in the calling pane's project. With `run`, Wings also presses Enter, but only while "Let Claude run commands in new tabs" is on in Settings, Agents (off by default). The reply says whether it ran. With the run setting off, `open_pane` only types a command, so nothing runs outside Claude Code's own permission checks for Bash. With it on, a command Claude passes with `run` runs in the new tab without those checks. The socket is readable by your user only (`0600`) and there is no network access.

### Claude Code hooks

A plugin can add context when a Claude Code session starts and refuse a Bash command, so Claude uses a plugin's tools without being told to. MCP instructions alone are often not enough. List the event in `contributes.hooks` and answer it in `main`:

```js
wings.onHook("SessionStart", (input, { project }) => (project ? `Track work in ${project.name} with the issues__* tools.` : null));
wings.onHook("PreToolUse", (input) => (/\bgit commit\b/.test(input.tool_input?.command ?? "") ? { deny: "Log the work in an issue first." } : null));
```

Connect adds `wings hook` to `SessionStart`, `UserPromptSubmit` (from 0.1.77) and `PreToolUse` in `~/.claude/settings.json`, after the hooks you already have, which stay as they are and in order. `PreToolUse` runs for every tool from Wings 0.2.68, in subagents too (their input has `agent_id`); before, it ran for Bash only, so a handler that reads `tool_input.command` should check `tool_name`. For a chat's session, which never runs the status line, `session.account` names the Claude Code account its tab runs (null for the default one). Disconnect takes it out again. Wings answers only for the plugins that are on, approved and list the event; with none it replies at once. `wings hook` waits up to 2 s for Wings, and with Wings closed, slow or with nothing to say it prints nothing, so a hook never blocks Claude. Contexts from several plugins are joined with a blank line (Claude Code keeps up to 10,000 characters), and for PreToolUse any deny refuses the command, with the reasons joined. Needs Wings 0.1.54.

`Journal` is not a Claude Code hook and Wings never installs it there. It is for a tool that records, at the end of each agent turn (Claude Code or OpenCode), which files changed and which commits the turn made, and runs a sink command with that as one JSON object on stdin. Wings registers itself as the journal's sink: on start (release builds) and after Connect it writes `{ "command": ["<path to wings>", "journal"] }` to `~/.config/journal/sink.json`, keeping any other keys, and repoints it if the app moves. A sink of your own in that file (any other command) is never touched, and a file that isn't a JSON object is left alone. Disconnecting both Claude Code and OpenCode in Plugins takes Wings' own entry out again (and the file, if nothing else is in it). To set it by hand, the command is `/Applications/Wings.app/Contents/MacOS/wings journal`. Wings adds `"hook_event_name": "Journal"` and passes it to the plugins that list `"Journal"`, as the pane the agent runs in: the sink's parent processes must reach that pane, which they do when the journal hook is a child of the agent. The input has `session_id`, `cwd`, `agent` (`"claude-code"` or `"opencode"`, which is also the `session.kind` the handler sees), `prompt` (the first 200 characters of the turn's prompt), `files` (`{ path, what }` each), `more` (changed files beyond those listed) and `commits` (short hashes, oldest first); the last two may be missing. A handler's answer is ignored, and `wings journal` prints nothing and exits 0 whether or not Wings is open. Wings waits 1.5 s per plugin, so answer quickly. Needs Wings 0.1.61.

The `wings-plugin-sdk` package has types for all of this.

## Pausing polls

Wings is in the background most of the day, and a timer that runs `git`, `gh` or `lsof` then spends the user's battery on a badge nobody sees. Stop timers while `wings.focused` is false and check once when it turns true. `pollWhileFocused(tick, ms)` from `wings-plugin-sdk/poll` does this: it runs `tick` every `ms` while Wings is in front, and once as soon as you come back, if `ms` has passed since the last run. Within `ms` it waits for the time that was left, so switching windows doesn't fetch on every switch. A third argument `{ immediate: true }` also runs `tick` once at the start, when Wings is in front. Keep event-driven work (`onPanes`, `onTranscript`, actions, tools) running. `onFocus` also tells you when to call `wings.notify`: send it only when `wings.focused` is false, since a user who is looking doesn't need a notification.

## Required tools

A plugin needs the GitHub CLI (`gh`), the GitLab CLI (`glab`) or the Azure CLI (`az`) when its `exec` or `post` entries name it. Its page in Plugins lists them under Needs, each Installed or not. A missing one has a button: on a Mac with Homebrew, Wings asks, then opens a tab in the project on screen and runs the vendor's own Homebrew command there (`brew install gh`, `brew install glab`, `brew update && brew install azure-cli`), so you see its output and can answer it. Without Homebrew, or off macOS, it links to the vendor's install page and to brew.sh. When the command is done, Wings checks again, says so, and restarts the plugins that run it.

`exec` rejects with `<program> is not installed or not on PATH` for a missing program. Don't match on that text or write the sign-in handling by hand: `cli()` from `wings-plugin-sdk/cli` runs `az`, `gh` or `glab`, tells a missing program and a signed-out one from a failed call, and `problemBadge` gives the badge with Install, Sign in and Try again. Its actions call `install()`, which asks Wings through `wings.installTool(program)`, `signIn()` and `retry()`. List each command in `permissions.exec`, `az login` and `gh auth login` included. `pr-tracker/src/main/badges.ts` draws the badge and answers its actions. A plugin in Rust uses `cli::Cli` of the Rust SDK, as `work-item/rust/src/az.rs` and `main_frame.rs` do. The commands come from Wings' own table, so a plugin only names the program: one in its manifest and in that table, and Wings always asks first.

## Views

A view is one of your pages that can open somewhere other than the sidebar. This one opens in a modal from its title bar button, and can move to a window of its own:

```json
"contributes": {
  "views": [{ "id": "board", "title": "Board", "icon": "list", "page": "dist/board.html", "opens": ["modal", "window"], "width": 720, "height": 520 }]
}
```

Any of the plugin's pages can open it, and keep it current while it's open in any of those places:

```js
await wings.openView("board", { as: "window" });
wings.broadcast({ refreshed: Date.now() }); // the board page hears it with wings.onBroadcast
```

A window shows the same sandboxed page as the sidebar would. Its calls go to Wings' main window and are checked there against your manifest, exactly like the sidebar's, so a window can't do more than the plugin could.

With `tab` in `opens`, the view opens as a tab in the project on screen, next to its terminal tabs, and fills the pane area. Each project has at most one tab per view, and opening it again shows that tab. The page keeps running while another tab shows, and stops when you close the tab, with its close button, a middle click or ⌘W, or when the plugin calls `wings.closeView`. Wings saves the tab with the others and opens it again on the next start, unless the plugin is gone or the view no longer lists `tab`.

Wings 0.1.14 and older refuse a plugin with `tab` in `opens`, so set `"minWingsVersion": "0.1.15"` to use it.

A view with `"newTab": true` also shows in the + menu, a chevron next to the + button, with the plugin's icon, and in the command palette as "New tab: <title>". Under Settings, General, "New tab button opens" picks what the + button itself opens: a terminal (the default) or one of these pages. `"multiple": true` makes an open of the view, from + or `openView`, a new tab instead of showing the project's existing one, except that an open with `args` equal to those of a tab of it already in the project shows that tab. Give each tab its own `wings.setTabState` so they don't share. `newTab`, `multiple`, `args`, `project`, `placement` and tab state need Wings 0.1.22, so set `"minWingsVersion": "0.1.22"` when you use them.

## Project sections

A plugin can list things under each project in the sidebar, like its open tasks or pull requests. Declare the section in the manifest, then fill it per project from the main script:

```json
"contributes": { "projectSections": [{ "id": "open", "title": "Open tasks", "icon": "todo" }] }
```

```ts
wings.onProjects((projects) => {
  for (const p of projects) {
    wings.setProjectSection(p.id, "open", [
      { id: "t1", label: "Fix the login", detail: "due Friday", badge: { text: "High", tone: "warning" }, open: { view: "board", args: { task: "t1" } } },
    ]);
  }
});
```

A section shows under its project after the project's row, with the plugin's icon, its title and the row count, only while it has rows. Clicking its header folds it shut, and Wings remembers that per project and section. Clicking a row opens `open.view` as a tab in that row's project, switching to the project, with `args` for `viewArgs()` and following the same rules as `openView`: a tab already open with other args takes the new ones and reloads, and a view with `multiple` opens a new tab unless a tab of it in that project already has equal `args`. `open.view` must be one of the plugin's views with `tab` in `opens`, or the call rejects. Wings cuts text for you (label and detail 120 characters, badge 24, ids 64), keeps the first 50 rows, leaves out a row with no `id` or `label` or an `id` already used, and rejects `args` over 16 KB. A badge `tone` is one of the badge tones. Sections are kept in memory, not saved: they go when the plugin is turned off or removed, so fill them again on start, and a call that repeats the last one for that project and section does nothing (the frame skips it from Wings 0.1.50, and Wings ignores identical rows before that), so call `setProjectSection` whenever you have looked and keep no copy of what you sent. They need Wings 0.1.23, so set `"minWingsVersion": "0.1.23"`.

## Blocks

A block is a plugin page the user places on a project's Project page, between its sections, like a sprint board or the open pull requests. Each block runs in its own sandboxed frame, with the same `wings` object as a tab page.

```json
"contributes": {
  "views": [{ "id": "board", "title": "Board", "page": "dist/board.html", "opens": ["tab"] }],
  "blocks": [{ "id": "board", "title": "Sprint board", "page": "dist/block.html", "minHeight": 200 }]
}
```

Give a block its own page, a `.wasm` frame that `contributes.blocks` names. `wings.placement()` says `"block"` where a compact version is wanted. Declaring a block adds nothing to the sidebar or the + menu: it shows only in the Project page's "+ Add" menu, for plugins that are on and approved.

In a block:

- `wings.project()` is the Project page's project, and never changes.
- `wings.blockState()` and `wings.setBlockState(state)` keep a small JSON value (up to 16 KB) per block, like the filter it shows. Two blocks of the same page have their own state. Wings saves it with the Project page.
- `wings.setHeight(px)` sizes the block to its content, within `minHeight` and 1200. Wings applies the height without reloading the page, and the call returns at once.
- Outside a block, `blockState()` gives `null`, and `setBlockState` and `setHeight` fail with a message saying so.

Blocks cost a frame each, so Wings loads one only when it scrolls into view, unloads it after 5 minutes out of view (a page that saved its state with `setBlockState` comes back as it was) and shows at most 8 at once on a Project page. While a block is out of view, or its project's tab is hidden, its `wings.focused` is false from the first line of the page (not only after the first `onFocus`) and `onFocus` reports each change, so `pollWhileFocused` pauses its polling and checks once when the block is back. Gate polling on `wings.focused`, not `document.visibilityState`: a frame scrolled out of view or in a hidden tab still reports `"visible"`, because the browser only reports the state of the whole Wings window. Don't poll from a block's page faster than you would from a sidebar.

Blocks, `"block"` and the three calls need Wings 0.1.24, so set `"minWingsVersion": "0.1.24"`. Older Wings ignore `contributes.blocks`.

## Popovers

A sidebar can have a quick look: a second page shown under its title bar button after you point at it for a moment, or when the button gets the keyboard. Clicking the button still opens the sidebar, and the popover doesn't show while that sidebar is open. It closes shortly after the pointer leaves both, or with Escape on the button.

```json
"contributes": {
  "sidebars": [{ "id": "timer", "title": "Timer", "icon": "clock", "page": "dist/sidebar.html", "popover": { "page": "dist/popover.html", "width": 340, "height": 420 } }]
}
```

The page gets the same `wings` object, storage and broadcasts as the sidebar. It loads the first time it shows and keeps running while closed, so it opens at once after that and its timers keep going. Send the user to the full view with `wings.openView("timer")`.

## Settings page

A plugin can have a page in Wings Settings instead of a settings form in its sidebar:

```json
"contributes": {
  "settings": { "page": "dist/settings.html" }
}
```

Any of the plugin's pages, or its main script, can send the user there, and hear what changed with `wings.onBroadcast`:

```js
await wings.openSettings();
// the settings page, after saving. A value like this is a `setting()`, see Talking to main:
await wings.storage.set("interval", 60);
wings.broadcast({ settingsChanged: true });
```

Wings 0.1.14 and older ignore `contributes.settings` and have no `wings.openSettings`. Set `"minWingsVersion": "0.1.15"` when the plugin needs them, or check `typeof wings.openSettings === "function"` first.

## Status line

Claude Code sends its status line command a JSON status after each reply: the 5-hour and weekly usage limits, the context window and how much of it is used, and the prompt cache. It's the documented way to get the usage limits, with no sign-in token involved. Wings keeps the newest status for plugins with `permissions.statusline`, and only the fields listed under `wings.statusline()`.

A status line's limits are from its session's last reply, so they lag behind. The native app also reads each account's limits the way Claude Code's `/usage` does, once a minute while Wings is in front and not at all behind other apps, for each Claude account with a session on screen or that reported, except one a plugin reported within the minute (`wings.reportUsage`): `GET https://api.anthropic.com/api/oauth/usage`, an endpoint Anthropic doesn't document, with that account's claude.ai login. It reads the login where Claude Code keeps it (on macOS the login keychain, with `security` as Claude Code does, else the account folder's `.credentials.json`), only for that request, and never refreshes it: an expired login, a 401 or a keychain you denied leaves the status line's numbers. What comes back joins the status line's limits by the same newest-data rule, so `wings.statusline()` resolves the same shape. No plugin ever sees the login.

When Wings starts, it adds itself to Claude Code: its MCP server, `wings statusline --pass` in front of the `statusLine` command in `~/.claude/settings.json`, and, from 0.1.54, `wings hook` after your `SessionStart` and `PreToolUse` hooks (see [Claude Code hooks](#claude-code-hooks)). Your own status line stays in that command and runs after Wings on the same input, so it still shows, your hooks stay as they were, and the rest of the file is left as it was. Disconnect in Plugins puts your status line back, takes the hooks out and stops Wings adding itself again. Dev builds don't connect on their own, since they'd point Claude Code at their own binary.

## Storage

`wings.storage` needs no permission: it's the plugin's own data, and no other plugin can read it. Wings keeps it in a folder per plugin, `<app data>/plugin-storage/<id>.<scope>/` (on macOS `~/Library/Application Support/dev.wings.app/plugin-storage/`), with one file per key, so a `set` writes only that key. Each change writes a new file and renames it into place, so a crash never leaves half a file. Before Wings 0.1.50 a plugin's storage was one file, `<id>.<scope>.json`; the first use after an update splits it into the folder and keeps the old file as `<id>.<scope>.json.migrated`. The main script and the sidebar pages share it, and writes they make at the same time all land.

It follows the same rule as secrets. An update from the same GitHub repo keeps it. Removing the plugin deletes it, and so does installing a plugin with the same id from a file or another repo, which gets a new `<scope>`, so a different package can't read what the old one stored. Keep tokens in `wings.secrets`, not here.
