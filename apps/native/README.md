# Wings native

An opt-in GPUI desktop executable. This independent Cargo project does not replace or change `apps/desktop`.

Build both the native app and its fixed sibling worker from the repository root:

```sh
cargo build --manifest-path apps/native/Cargo.toml --bins
apps/native/target/debug/wings-native \
  --project /exact/saved/project/path \
  --issues-storage-root /existing/plugin/storage \
  --issues-scope TRUSTED-INSTALL-SCOPE
```

The storage root and installation scope must be supplied together. Use the trusted existing Issues installation's values. The app does not discover or infer them from the plugin id. Without these options, it shows setup instructions, not sample issues.

`--project` defaults to the current directory. An absolute project path is kept exactly as supplied, including its symlink spelling, so use the same path as the existing saved project. Relative paths are made absolute without resolving symlinks. `--help` lists the options.

## macOS package staging

```sh
cd apps/native
sh scripts/package-mac-app.sh
node --test scripts/package-mac-app.test.mjs
```

`package-mac-app.sh "Release notes"` builds the archive, `native-latest-darwin-<architecture>.json` and its detached `.sig`, and `native-latest-darwin-<architecture>.v2.json` (the same with the terminal server's `server_version`) and its `.sig` in `target/release/bundle/macos/darwin-<architecture>/`. It requires `WINGS_UPDATER_KEY` (default `~/.tauri/wings-updater.key`) and uses the desktop's Tauri signing CLI and embedded public key. Run `sh scripts/build-mac-app.sh` when you only need a local bundle. The native app uses its own `[package]` version from `apps/native/Cargo.toml`, not the desktop version used for plugin compatibility. `WINGS_SWITCH=1` before either script builds the replacement instead: `Wings.app` with the desktop's bundle id and version, on the desktop's data folder, with its first start bringing over what this app kept in `Wings Native/` (`src/data_dir.rs`, [docs/switch-to-native.md](../../docs/switch-to-native.md)).

The bundle carries `wings-native`, `wings-plugin-worker` and `wings`, and the terminal server in a helper app, `Contents/Library/Wings Terminals.app` (bundle id `dev.wings.terminals`; the side-by-side app's is `Wings-native Terminals.app`, `dev.wings.native.terminals`), signed with the app. A copy of `wings-terminal-server` stays in `Contents/MacOS` only because the updaters of earlier apps require it. Updates require the four executables (the helper app's, not that copy) to support the running Mac's architecture.

Packaged release builds check on startup and every six hours while focused. App menu > Check for Updates… and the command palette open the native update dialog. Download update authenticates the metadata, archive and staged bundle off the UI thread. Install and restart saves the workspace through normal quit, waits for the app process to exit, atomically exchanges the bundles and relaunches the exact installed executable with its original arguments. Terminals in the terminal server keep running and the relaunched app attaches them again; terminals running inside the app, and their agents, may stop. Source/debug runs explain why automatic installation is unavailable. Nothing is installed without confirmation.

## Terminals that outlive the app

A release build runs new terminals in `wings-terminal-server` (`src/terminal_server.rs`, the `wings-ptyd` crate), so they keep running when the app quits, crashes or updates, and the next launch attaches them again by their saved history id. Settings > General > "Keep terminals running when Wings quits" turns it off for new terminals; terminals the server already runs are still attached and keep running until closed. `WINGS_TERMINAL_SERVER=1` forces it on and `=0` forces it off, over the setting. A debug build keeps terminals in the app unless `WINGS_TERMINAL_SERVER=1`, because it shares the side-by-side app's settings, and tests set `Config::terminal_server` themselves.

The server runs from a copy of the helper app at the data folder's `terminal-server/Wings Terminals.app`, never from the bundle an update deletes, and the path stays the same across updates. The app copies it when the executable or `Info.plist` there differ from the bundle's. An app with the same server version uses the running server. An app with a newer one replaces the copy, moving the old one to `terminal-server/replaced/`, and tells the old server to drain: its terminals keep running from the copy put aside and are attached as before, new ones go to the new server, and the old server exits once its last terminal ends. A launch deletes the copies no server runs from, which it tells by each server's process: those in `replaced/`, and the bare `bin/wings-terminal-server` copies apps before the helper app made. `tests/terminal_server.rs` (`an_update_keeps_the_panes_running_and_the_new_app_attaches_them_again`) plays this through with an older app's server and three builds' helper apps in a temp folder.

An older, draining server's terminals keep its permissions until they end, so a pane on one says "older server" in its header, and Settings > General lists every server with its terminals (in Wings' panes, or not shown anywhere) and a Stop button for an older one (`src/workspace/older_servers.rs`). Nothing that runs a program is ended on its own: at launch, an older server's idle shells that no saved pane names end, and when it runs only idle shells they all end and their saved panes start again in the current server below what they printed (`Servers::tidy_older`). While the app runs, once everything on an older server is an idle shell or an idle agent with a session to resume, its panes move to the current server in the same tab with their output kept, and the agents exit with `/exit` and resume there; a pane you're typing in or that has the keys waits. It's checked when the agent detection sees a program or agent change and when a pane closes, never on a timer. The update dialog says what happens to open terminals when a release brings a newer server: the `.v2.json` feed names it (`server_version`), and a server started without launchd leaves `terminal-server/v<version>.direct` with its pid.

Programs in the server's terminals can't read other apps' data, like Chrome's profile that the Chrome DevTools MCP reads, and macOS never asks. Turning on that app's data for Wings Terminals in System Settings > Privacy & Security > Files & Folders lets them: macOS lists the helper app there by its bundle id, with a switch for each app whose data its terminals asked for, which it doesn't do for a bare program (that switch turns itself off again). At launch the app runs `wings-terminal-server check-access` under the server's own privacy responsibility, which lists Chrome's data folder (and so puts Chrome's switch under Wings Terminals). When that's refused, the app asks once with a dialog whose button opens Files & Folders; without Chrome it can't tell and shows nothing. Settings > General keeps the same button (`src/workspace/disk_access.rs`).

Publish the five staged files yourself in `josippapez/Wings` under `native-v<version>` and make that release latest. The fixed feed URL is `https://github.com/josippapez/Wings/releases/latest/download/native-latest-darwin-<architecture>.json`; apps after 0.2.10 read the `.v2.json` beside it first. Include both architecture feeds when shipping both. Native never reads desktop `latest.json`. See [releasing](../../docs/releasing.md) for the signed contract and recovery.

Checks:

```sh
cargo fmt --manifest-path apps/native/Cargo.toml -- --check
cargo test --manifest-path apps/native/Cargo.toml --no-default-features
cargo test --manifest-path apps/native/Cargo.toml --lib plugin_view::tests
cargo test --manifest-path apps/native/Cargo.toml --features test-support --lib
cargo build --manifest-path apps/native/Cargo.toml --bins
cargo run --manifest-path apps/native/Cargo.toml --example shot --features test-support -- OUT_DIR
```

The `shot` example renders the window offscreen with real Metal rendering at 1000 and 640 points wide and saves tabs, splits, find and Issues as PNGs. Nothing shows on screen and focus doesn't move. It's macOS only.

GPUI and its platform backend are pinned to the `gpui-pre` 0.3.11 snapshot. The platform crate enables `font-kit` for macOS glyph rendering and `runtime_shaders` to compile Metal shaders at runtime rather than requiring the Metal command-line compiler. Linux backends enable Wayland and X11. Platform builds still need their native development tools.

The Issues view reads only the selected `tasks` installation namespace. Every Refresh loads a fresh read-only snapshot and invokes the reviewed built-in TypeScript bundle in the separate QuickJS worker. Disk reads and worker IPC run on GPUI's background executor. The app does not write or migrate storage. A snapshot is not atomic with concurrent desktop writes. Malformed data and size limits produce an error, not a partial or silently empty list.

A sidebar lists the native app's own projects (`Wings Native/spaces.json`, beside the workspace file; the first run copies the desktop app's `spaces.json` in once, and the desktop's file is never read or written after that): pinned ones first, worktrees under their project, each with its git branch. Clicking one shows that project's tabs; the project you leave keeps its tabs and running shells. Cmd-B or Cmd-\\ toggles the sidebar. The window has terminal tabs and an Issues tab, which the tasks plugin's board takes the place of when that plugin runs. Each terminal runs your shell in the project folder and is named by the title its program sets. The tab keys match the desktop app: Cmd-T opens a terminal, Cmd-W closes it and its shell, Cmd-] and Cmd-[ go to the next and previous tab, and Cmd-1 to Cmd-9 go to a tab by position (Ctrl-Shift instead of Cmd elsewhere). Panes split like the desktop's: Cmd-D splits right, Cmd-Shift-D splits down, Cmd-W closes the focused pane and its shell (the tab closes with its last pane), and Cmd-Option-arrows move focus to the pane on that side. Each pane is a card with its title and split, zoom and close buttons. Double-click a title to name the pane (Enter keeps it, an empty name goes back to the program's title, Escape cancels); names are saved. Tab > Move Tab Left/Right reorders terminal tabs. Zoom (also Pane > Zoom Pane) fills the tab with the pane until you zoom out, split, or focus another pane. Dragging the gap between panes resizes them, keeping each side between 15% and 85%. Tabs, splits, sizes and focus are saved per project after every change and come back on the next launch, each pane with a new shell in the folder its shell was last in (the project folder if that's gone). Quitting saves once more, so a `cd` since the last change is kept, and saves each pane's last 1 MiB of output (`scrollback/` beside the workspace file), which the next launch shows above the new shell. Modes the old program left on are switched off first, and nothing in the old output can answer into the new shell or write the clipboard. The file is `Wings Native/workspace.json` in the platform's app data folder (`~/Library/Application Support` on macOS). The native app never writes the desktop app's workspace file. The menu bar matches the desktop app's (File, Edit, Tab, Pane, View, Window, plus the app menu on macOS), and every shortcut is a menu command with its key shown, including Cmd-Q. The wheel and Shift-Page Up/Down scroll its history. Dragging selects, double-click selects a word and triple-click a line. Cmd-C and Cmd-V copy and paste (Ctrl-Shift-C and Ctrl-Shift-V elsewhere). Programs that ask for the mouse get clicks and the wheel instead. Programs can write the clipboard but not read it. Hovering a web link underlines it, and Cmd-click or Ctrl-click opens it. Shift-Return sends Meta-Return (a new line in Claude Code). On macOS, Option-Left/Right move a word, Cmd-Left/Right go to the line start and end, and Cmd-Backspace deletes to the line start. Settings, Keyboard's "Use Option as Meta" picks off, the left Option key, the right one or both, and the other Option key types characters. Cmd-+ and Cmd-- change the terminal font size from 9 to 24 and Cmd-0 resets it to 13, as in the desktop app, and the size is saved. Cmd-F (Ctrl-Shift-F elsewhere) opens find over the history, with match case, regular expressions, "N of M" up to 1000+, Enter and Shift-Enter for next and previous, and Escape to close. The current match stays on its text when output arrives or the window resizes. A pane hidden for 10 minutes keeps its scrollback as text (about 0.5 MB instead of about 51 MB for 10,000 full lines) and gets it back when it's shown, as in the desktop app. On macOS the app starts itself once more with `MallocLargeCache=0`, because the system allocator otherwise keeps most of the freed memory. The `test-support` feature runs headless GPUI windows that send keys, mouse and wheel events through the real view. The built-in Issues view is read-only: a virtualized list, setup/loading/empty/error states and Refresh. It does not replace the desktop app or provide issue editing, search, board/detail views, third-party plugin compatibility, or complete keyboard/IME/screen-reader parity. Accessibility roles, names, keyboard activation and visible focus are implemented, not a conformance claim.

The window is drawn like the desktop app's: no system title bar, the traffic lights beside the sidebar button and the tabs in one row, the project and branch above the panes, and the desktop's blurred glass behind the sidebar on macOS. Every pane shows what runs in it, and agents (Claude Code, opencode, Codex) are detected like in the desktop app every half second: each pane, tab and project shows a status dot, and the sidebar lists the agents with what they're doing; a click goes to the agent's pane. Cmd-, (or the sidebar's Settings row) opens Settings: the terminal font, the cursor style and Shift-Return. Cmd-K (Ctrl-Shift-K elsewhere) opens the command palette, as in the desktop app: the commands the native app has with their keys, projects, tabs, agents, plugin pages and recent sessions in one list that narrows as you type (Up/Down or Ctrl-N/Ctrl-P and Home/End move, Enter runs, Escape closes); choosing a session resumes it in a new tab of the project that holds its folder. View > Past Sessions opens the history sheet: this project's or every project's Claude Code and OpenCode sessions, searched by words, last activity and branch, with Resume, Resume in this tab, Fork and Copy resume command. Controls come from `src/ui`, a kit named after the desktop's shadcn components (buttons, switch, input, card, setting row, dialog, status dot), with the desktop's Lucide icons in `assets/icons`.

The packaged worker is for the reviewed built-in only. A separate process is **not an OS sandbox** and must not be used to run arbitrary installed plugins. No HTML, Tauri, Wry or webview is used by this native UI; a plugin page is React rendered by `wings-plugin-ui/native` into a tree of data, never into a DOM. Memory, measured once on macOS with the same 36 panes and saved output as a desktop workspace, at the same window size: about 180 MB for the native app, about 1.3 GB for the desktop app and its WebKit processes. With all 36 panes full, the native app uses about 870 MB, and about 200 MB once the hidden panes have unloaded.

The default `ui` feature enables the optional GPUI and terminal dependencies. The library and worker build with `--no-default-features` without GPU dependencies. Keep `wings-native` and `wings-plugin-worker` together in the same executable directory. The `theme` module mirrors the existing desktop palette.

Plugins run with no WebView, and Rust draws their pages with the app's own UI. A plugin's code is TypeScript and React run in QuickJS inside the app, or Rust built to WebAssembly (`src/page/runtime/wasm.rs`, with the SDK in `packages/plugin-rs`): a frame's `dist/native/<name>.wasm` runs in place of its `<name>.js`. Rust is the way new plugins are meant to be written (decided 2026-11-12), and the TypeScript plugins keep running. A WebAssembly frame still has a thread of its own and the default limits, and the host boundary hasn't had its security review.

Plugin pages in React: `pages/pilot.tsx` uses `wings-plugin-ui/native`'s `Page`, `Toolbar`, `Button`, `Badge` and hooks, and `node apps/native/pages/build.mjs` bundles it with React and the page renderer into `pages/dist/pilot.js` (`--check` fails when that file is stale). `src/page/runtime.rs` runs a bundle in QuickJS on its own thread: the page sees only `wings.render(json)` and real `setTimeout`/`clearTimeout`, and a turn that uses more than a second of the CPU ends the page (time spent waiting, on a host call or a busy Mac, doesn't count). `src/page/tree.rs` checks each tree the page sends (unknown components are dropped, sizes bounded), and `PageView` draws it with `src/ui` and sends a click back to the page's handler by id, which renders again.

A plugin's main script and its pages run side by side: `PluginHost` (`src/page/plugin.rs`) starts the main bundle and any number of pages, each in its own QuickJS thread with the same budgets, so a frame that throws or never stops ends alone. A main that stops starts again by itself (`PluginHost::keep_main`), 2 seconds later and then twice as long after each short run, up to 10 minutes; a sidebar page that stops shows Reload by its error. Its frames talk with `wings.broadcast` and `wings.onBroadcast` as the desktop's do (JSON of at most 64,000 characters, to every other frame of the same plugin and nobody else, in order; `wings-plugin-sdk/messages` splits anything bigger) and share `wings.storage`, which is the desktop's `wings-plugin-storage` under the plugin's id and install scope, which the app passes as `PluginConfig`'s storage root and scope. A frame also gets `setInterval`, a `console` that discards its output, and `wings.focused` and `wings.onFocus`, which only say the window is focused. A frame of a plugin whose host has the plugin's manifest (`PluginHost::with_access`, which the window uses) also has `wings.onPanes`, `setBadge`, `setPaneStatus` and `onAction`, `exec`, `openUrl`, `ports`, `notify`, `transcript`, `onTranscript` and `statusline`, written as `apps/desktop/public/plugin-sdk.js` writes them and answered as the desktop's `handle` and `plugin_*` commands answer them (`src/page/plugin/calls.rs`): the permission is `wings-plugins`' to give (`permissions`, `exec`, `fetch::may_open_url`, `transcript`), with the desktop's argument rules and messages. A call that reads the disk or runs a program runs on a thread of its own and answers the frame's promise when it is done, so it never holds up the frame. `disks`, `diskFind` and `diskUsage` use the desktop's `wings-disk-usage` crate: a scan reports its progress while it runs, and stops when its frame ends or its `signal` aborts. Disk usage runs on them: its map is plugin-ui native's `Sunburst`, which the app draws from the wedges the page lays out (no zoom between folders, no dragging a wedge to the Collector, no keyboard shortcuts, and the list shows its biggest 120 rows with a button for more), beside a `Scroll` list in a `Split`. `statusline` has what Claude Code last told `wings statusline` (see Claude Code below), and `notify` ignores `actions`. A plugin's main also answers the tools other plugins call (`onTool`, and `callTool` between Wings' own plugins, with the desktop's checks), `closeView` closes a page wherever it shows in the project on screen, and `project` is the project on screen. `createWorktree`, `worktreeSetup` and `setWorktreeSetup` work on the app's own project list, with the desktop's checks and code (`crates/wings-spaces`): a worktree is made beside its repo, listed under its project in the sidebar, and its project's setup line is typed into the first pane a plugin opens there. `claudeAccounts` and `setClaudeAccount` list the Claude Code accounts and set the one each project uses, with the desktop's checks and code (`crates/wings-spaces`): a new terminal in a project starts with that account's `CLAUDE_CONFIG_DIR`, and `transcript`, `onTranscript` and agent detection read every account's folder. Settings, Agents connects Claude Code in that account too. `setProjectSection` fills the lists under each project in the sidebar (`src/workspace/project_sections.rs`). `fetch`, `secrets` and `post` are the desktop's (`src/page/plugin/calls/pr_tracker.rs`; `wings-plugins` checks the URL, headers, bearer and path; a request is `ureq`'s with no redirects and a 30 s limit), with the secrets in the system keychain under the desktop's service name, so a token saved in either app is there for both. The names a plugin stored are noted in `plugins.json`, as the desktop notes them, so removing the plugin deletes them. `sendToAgent` pastes the message, with the desktop's header and its checks, into the prompt of the agent in a pane, refuses one where you typed and haven't sent it, and presses Enter a moment later only while Settings, Agents' "Let agents message each other" is on, answering `{ submitted }`. It doesn't know whether you have typed into the prompt, which the desktop also refuses over. `openSettings` shows the plugin's settings page (`contributes.settings`, built to `dist/native/settings.js`) in a window of its own, not in Settings. `emit` and `onEvent` send an event from one of Wings' own plugins to the main of those that declared it. `onReply` is accepted and never called, since the native diff viewer has no reply box. `viewArgs` is what `openView` passed as `args` (only for a tab, up to 16 KB): a view that is open takes new args by starting over, a `multiple` view opens a tab unless one has the same args, and a tab's args are saved with it. The rest of the desktop's `wings` API (opening panes and views, diffs) isn't here until a native plugin needs it. `pages/fixture/` is a plugin written like the real ones, with `channel` and `useQuery`: `node apps/native/pages/build.mjs` builds `pages/<name>.tsx` and each plugin folder's `main.ts` and `page.tsx` (and `<name>-page.ts`) into `pages/dist/`.

The window runs the desktop's plugins (`src/installed.rs`). It owns the desktop's data folder (`dev.wings.app`) as the desktop does: `wings-plugins`, the desktop's own crate, loads the folders in `plugins/` with the desktop's rules, and `plugins.json` says which are turned on and whether their permissions are approved, so a plugin runs here exactly when it runs there. A plugin with a native build (`dist/native/main.js`, which the plugin build writes for a manifest with `"native": true`) has its main started in a `PluginHost` with the desktop's `plugin-storage/` folder and the install scope `plugins.json` names, so what it saves is shared with the desktop (a plugin installed here gets its scope when it is installed, as on the desktop). A plugin without that file isn't ported and is skipped without a message, and so are plugins the desktop skips. Settings, Plugins installs from a GitHub link (a repo, its release's `.wings-plugin`, or a plugin folder in a repo) or a `.wings-plugin` file, shows what each plugin may access, asks with "Turn on <plugin>?" before one runs and again when an update asks for more, turns plugins on and off, checks GitHub for newer versions, updates, reinstalls and removes, all through `wings-plugins`' `Store` with the desktop's checks (`src/workspace/plugin_manage.rs`); `wings plugin install|link|update|enable|disable|remove` does the same over the socket. A change starts or stops the plugin's main and pages at once. A plugin on without a native build shows "On · No native build". Dropping a `.wings-plugin` file on Settings, Plugins installs it too, and a plugin's README shows on its page. Not here: the "needs" tool installs on a plugin's page. `minWingsVersion` is checked against the desktop's version, which `build.rs` reads from `apps/desktop/src-tauri/Cargo.toml` (this crate's own `0.1.0` would be wrong, and a constant would need an edit with every desktop release). A view that opens as a tab, sets `newTab` (what the desktop's + menu lists) and has a native page `dist/native/<page>.js`, for the page file the manifest names (`dist/board.html` is `board.js`), is listed in the + menu and under the project sections. Opening it makes a tab after the terminals, named after the view and running a frame of its plugin until the tab closes (Cmd-W or its X), once per view and project unless the view sets `multiple`. Switching projects keeps each project's pages running, Cmd-] and Cmd-1..9 reach them, Move Tab swaps them among themselves, and the open pages are saved with the tabs and come back on the next launch unless their plugin has been turned off. A plugin's sidebars (`contributes.sidebars`, built to `dist/native/<page>.js` like a view's page) get a title bar button each, at the right end, which opens the page in a panel on the right (360 points to start, dragged by its left edge between 250 and 640 points, and the panes keep 320 beside the project sidebar while the window has room, with the width saved); the page keeps running while the panel is closed, and a click on a status strip that names the sidebar opens it. Plugins draw on panes as the desktop's do: a `badges` plugin's pill in the pane header opens a card with its rows and buttons, and a click on a button is the main frame's `onAction` (the button waits for it, and shows the error it throws), and a `status` plugin's strip under the terminal shows its items, with the rows in a card on hover. A notification goes through `osascript` on macOS (`notify-send` elsewhere), which needs no app bundle; where that fails it is shown in the window instead. The panes are told to plugins as the window draws, when something about them changed (about 4 µs on a quiet frame with 20 panes in an optimized build). Transcript entries come from following the transcripts of the Claude sessions found in panes (`src/transcripts.rs`, the desktop's tailer ported), only while a running plugin may read transcripts. `wings.ports` is the desktop's lookup ported (`src/ports.rs`). `wings.agentActivity` asks OpenCode's background service as the desktop does (`wings_agents::agent_activity`, moved out of the desktop so both use it), and `wings.onAgentActivity` hears which OpenCode session did something, one event per burst of calls, only while a running plugin may read agent activity. A debug build takes `--plugins-dev-root PATH` to run the plugins of a folder as well, as the desktop's debug builds run the repo's `plugins/`: `cargo run --manifest-path apps/native/Cargo.toml -- --plugins-dev-root plugins` runs dev-servers and HUD from the repo, always on and approved, a plugin the desktop has no record of storing what it saves under the scope `dev`. `cargo run --example shot_plugins --features test-support -- <out-dir>` renders a badge, its card, a strip and a sidebar offscreen, and with `--changes`, `--schedules`, `--pr-tracker`, `--session-detail` or `--disk` those plugins' pages over made-up data. Not done yet: a `noProject` view, and picking up a plugin the desktop app installs or turns on while this app runs. `Config.plugins` holds the folder, state file and storage root, as `projects` and `state` hold theirs; tests and the `shot` example point them at temp folders.

Claude Code connects to this app exactly as it connects to the desktop's, so swapping the apps changes nothing in its config (`crates/wings-connect`, which both apps use). `cargo build --bins` also builds `wings`, the desktop's `wings` command, which the bundle carries beside `wings-native` (`scripts/install-mac-app.sh`): `wings --mcp <socket>` is Claude Code's MCP server, `wings statusline` is chained in front of your status line, `wings hook` runs after your SessionStart, PreToolUse (Bash) and UserPromptSubmit hooks, `wings journal` is the change journal's sink, and `wings plugin`, `wings tools`, `wings <plugin> <tool>`, `wings wait` and `wings worktree-setup` are the CLI. All of them talk to the running app over the desktop's socket, `mcp.sock` in the desktop's data folder (`dev.wings.app`); the app keeps its own state in `Wings Native/`. On start the app serves that socket as the desktop does, replacing one an earlier run left, and a release build of the installed app connects Claude Code to its own `wings`, in the default account and each account a project uses, unless you disconnected it (`Wings Native/claude-disconnected`): the MCP server is registered with `claude mcp add` at user scope, and the status line and hooks are chained with yours and put back byte for byte on Disconnect. Settings, Agents shows each account's state and has Connect, Reconnect, Disconnect and "Load Wings tools at session start". Its "Session names and summaries" picks the model on this Mac (Apple's on-device one, an Ollama model, or off) that names untitled sessions in the history sheet and the palette and puts a one-line summary of each agent's last turn under it in the sidebar, as on the desktop (`wings_agents::ai`, which both apps use). The choice and the names are the desktop's `ai/` folder. "Put idle agents to sleep" (on, after 15 minutes, as on the desktop) ends an idle Claude Code or opencode in a pane out of sight with its own `/exit`, unless something it started still runs or text waits in its prompt. The pane stays in the Agents list as sleeping, keeps its session across a restart, and resumes it when shown (`workspace/sleep.rs`). The socket answers Wings' own tools (`search_history`, `read_session`, `list_sessions`, `read_pane`, `open_pane`, `close_pane`, `send_to_agent`, `notify`, `worktree_setup`, `project_info_*`) against this window's panes, agents and projects, and the tools of the plugins that run here; a hook goes to the `wings.onHook` of the running plugins that declare it, and a status line to `wings.statusline()`. `open_pane` presses Enter after the command only while "Let Claude run commands in new tabs" is on, and `send_to_agent` only while "Let agents message each other" is on (both in Settings, Agents, off by default as on the desktop). Called from a pane, `open_pane` opens below it, to its right or floating over it as "Agent terminals open" in Settings, Agents says, and the agent's next ones beside the last, with the keys left with the agent; a command goes to a terminal the same agent opened that sits at its prompt instead. The buttons on such a terminal hide it (the button on the agent's pane brings it back), move it below or to the right, or float it over the agent in a panel you move by its header, resize from its corner, minimise and dock back, as on the desktop (`workspace/agent_terminals.rs`). Which pane opened which, and whose terminals float, last until the app quits, as on the desktop. `worktree_setup` with a new setup command asks you with "Allow this setup command?" and saves nothing until you allow it, one prompt per project at a time, with Allow armed after a second. `close_pane` closes only panes of the project on screen that Claude opened. Settings, Agents also connects OpenCode, with Connect and Disconnect. `Config.socket` is set only by `main`, so tests and screenshots never take the socket of the Wings you use or touch Claude Code's settings.

Plugin checks run 20 seconds after launch and every six hours from launch. A check due while unfocused waits until activation. GitHub updates are announced once per version per session, never installed automatically. Review opens Settings, Plugins. The Available list shows compatible plugins from the official Wings repository and uses the usual install and permission review. Newly available plugins are announced once, with seen ids saved across launches. Check for updates refreshes both lists. Render these states without network access with `cargo run --example shot --features test-support -- <out-dir> plugin-updates` from `apps/native`.
