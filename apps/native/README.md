# Wings native

An opt-in GPUI desktop executable. This independent Cargo project does not replace or change `apps/desktop`.

Build both the native app and its fixed sibling worker from the repository root:

```sh
cargo build --manifest-path apps/native/Cargo.toml --bins
apps/native/target/debug/wings-native \
  --project /exact/saved/project/path \
  --issues-storage-root /existing/plugin/storage \
  --issues-scope TRUSTED-INSTALL-SCOPE
```

The storage root and installation scope must be supplied together. Use the trusted existing Issues installation's values. The app does not discover or infer them from the plugin id. Without these options, it shows setup instructions, not sample issues.

`--project` defaults to the current directory. An absolute project path is kept exactly as supplied, including its symlink spelling, so use the same path as the existing saved project. Relative paths are made absolute without resolving symlinks. `--help` lists the options.

## macOS package staging

```sh
cd apps/native
sh scripts/package-mac-app.sh
node --test scripts/package-mac-app.test.mjs
```

`package-mac-app.sh "Release notes"` builds the archive, `native-latest-darwin-<architecture>.json` and its detached `.sig` in `target/release/bundle/macos/darwin-<architecture>/`. It requires `WINGS_UPDATER_KEY` (default `~/.tauri/wings-updater.key`) and uses the desktop's Tauri signing CLI and embedded public key. Run `sh scripts/build-mac-app.sh` when you only need a local bundle. The native app uses its own `[package]` version from `apps/native/Cargo.toml`, not the desktop version used for plugin compatibility.

The bundle carries `wings-native`, `wings-plugin-worker`, `wings` and `wings-terminal-server`. Updates require all four executables to support the running Mac's architecture.

Packaged release builds check on startup and every six hours while focused. App menu > Check for Updates… and the command palette open the native update dialog. Download update authenticates the metadata, archive and staged bundle off the UI thread. Install and restart saves the workspace through normal quit, waits for the app process to exit, atomically exchanges the bundles and relaunches the exact installed executable with its original arguments. Running terminals and agents may stop. Source/debug runs explain why automatic installation is unavailable. Nothing is installed without confirmation.

Publish the three staged files yourself in `josippapez/Wings` under `native-v<version>` and make that release latest. The fixed feed URL is `https://github.com/josippapez/Wings/releases/latest/download/native-latest-darwin-<architecture>.json`. Include both architecture feeds when shipping both. Native never reads desktop `latest.json`. See [releasing](../../docs/releasing.md) for the signed contract and recovery.

Checks:

```sh
cargo fmt --manifest-path apps/native/Cargo.toml -- --check
cargo test --manifest-path apps/native/Cargo.toml --no-default-features
cargo test --manifest-path apps/native/Cargo.toml --lib plugin_view::tests
cargo test --manifest-path apps/native/Cargo.toml --features test-support --lib
cargo build --manifest-path apps/native/Cargo.toml --bins
cargo run --manifest-path apps/native/Cargo.toml --example shot --features test-support -- OUT_DIR
```

The `shot` example renders the window offscreen with real Metal rendering at 1000 and 640 points wide and saves tabs, splits, find and Issues as PNGs. Nothing shows on screen and focus doesn't move. It's macOS only.

GPUI and its platform backend are pinned to the `gpui-pre` 0.3.11 snapshot. The platform crate enables `font-kit` for macOS glyph rendering and `runtime_shaders` to compile Metal shaders at runtime rather than requiring the Metal command-line compiler. Linux backends enable Wayland and X11. Platform builds still need their native development tools.

The Issues view reads only the selected `tasks` installation namespace. Every Refresh loads a fresh read-only snapshot and invokes the reviewed built-in TypeScript bundle in the separate QuickJS worker. Disk reads and worker IPC run on GPUI's background executor. The app does not write or migrate storage. A snapshot is not atomic with concurrent desktop writes. Malformed data and size limits produce an error, not a partial or silently empty list.

A sidebar lists the native app's own projects (`Wings Native/spaces.json`, beside the workspace file; the first run copies the desktop app's `spaces.json` in once, and the desktop's file is never read or written after that): pinned ones first, worktrees under their project, each with its git branch. Clicking one shows that project's tabs; the project you leave keeps its tabs and running shells. Cmd-B or Cmd-\\ toggles the sidebar. The window has terminal tabs and an Issues tab. Each terminal runs your shell in the project folder and is named by the title its program sets. The tab keys match the desktop app: Cmd-T opens a terminal, Cmd-W closes it and its shell, Cmd-] and Cmd-[ go to the next and previous tab, and Cmd-1 to Cmd-9 go to a tab by position (Ctrl-Shift instead of Cmd elsewhere). Panes split like the desktop's: Cmd-D splits right, Cmd-Shift-D splits down, Cmd-W closes the focused pane and its shell (the tab closes with its last pane), and Cmd-Option-arrows move focus to the pane on that side. Each pane is a card with its title and split, zoom and close buttons. Double-click a title to name the pane (Enter keeps it, an empty name goes back to the program's title, Escape cancels); names are saved. Tab > Move Tab Left/Right reorders terminal tabs. Zoom (also Pane > Zoom Pane) fills the tab with the pane until you zoom out, split, or focus another pane. Dragging the gap between panes resizes them, keeping each side between 15% and 85%. Tabs, splits, sizes and focus are saved per project after every change and come back on the next launch, each pane with a new shell in the folder its shell was last in (the project folder if that's gone). Quitting saves once more, so a `cd` since the last change is kept, and saves each pane's last 1 MiB of output (`scrollback/` beside the workspace file), which the next launch shows above the new shell. Modes the old program left on are switched off first, and nothing in the old output can answer into the new shell or write the clipboard. The file is `Wings Native/workspace.json` in the platform's app data folder (`~/Library/Application Support` on macOS). The native app never writes the desktop app's workspace file. The menu bar matches the desktop app's (File, Edit, Tab, Pane, View, Window, plus the app menu on macOS), and every shortcut is a menu command with its key shown, including Cmd-Q. The wheel and Shift-Page Up/Down scroll its history. Dragging selects, double-click selects a word and triple-click a line. Cmd-C and Cmd-V copy and paste (Ctrl-Shift-C and Ctrl-Shift-V elsewhere). Programs that ask for the mouse get clicks and the wheel instead. Programs can write the clipboard but not read it. Hovering a web link underlines it, and Cmd-click or Ctrl-click opens it. Shift-Return sends Meta-Return (a new line in Claude Code). On macOS, Option-Left/Right move a word, Cmd-Left/Right go to the line start and end, and Cmd-Backspace deletes to the line start. Option is not Meta yet, because GPUI doesn't report which Option key is held. Cmd-+ and Cmd-- change the terminal font size from 9 to 24 and Cmd-0 resets it to 13, as in the desktop app, and the size is saved. Cmd-F (Ctrl-Shift-F elsewhere) opens find over the history, with match case, regular expressions, "N of M" up to 1000+, Enter and Shift-Enter for next and previous, and Escape to close. The current match stays on its text when output arrives or the window resizes. A pane hidden for 10 minutes keeps its scrollback as text (about 0.5 MB instead of about 51 MB for 10,000 full lines) and gets it back when it's shown, as in the desktop app. On macOS the app starts itself once more with `MallocLargeCache=0`, because the system allocator otherwise keeps most of the freed memory. The `test-support` feature runs headless GPUI windows that send keys, mouse and wheel events through the real view. Issues is a read-only first slice: a virtualized list, setup/loading/empty/error states and Refresh.  It does not replace the desktop app or provide issue editing, search, board/detail views, third-party plugin compatibility, or complete keyboard/IME/screen-reader parity. Accessibility roles, names, keyboard activation and visible focus are implemented, not a conformance claim.

The window is drawn like the desktop app's: no system title bar, the traffic lights beside the sidebar button and the tabs in one row, the project and branch above the panes, and the desktop's blurred glass behind the sidebar on macOS. Every pane shows what runs in it, and agents (Claude Code, opencode, Codex) are detected like in the desktop app every half second: each pane, tab and project shows a status dot, and the sidebar lists the agents with what they're doing; a click goes to the agent's pane. Cmd-, (or the sidebar's Settings row) opens Settings: the terminal font, the cursor style and Shift-Return. Cmd-K (Ctrl-Shift-K elsewhere) opens the command palette, as in the desktop app: the commands the native app has with their keys, projects, tabs, agents, plugin pages and recent sessions in one list that narrows as you type (Up/Down or Ctrl-N/Ctrl-P and Home/End move, Enter runs, Escape closes); choosing a session resumes it in a new tab of the project that holds its folder. View > Past Sessions opens the history sheet: this project's or every project's Claude Code and OpenCode sessions, searched by words, last activity and branch, with Resume, Resume in this tab, Fork and Copy resume command. Controls come from `src/ui`, a kit named after the desktop's shadcn components (buttons, switch, input, card, setting row, dialog, status dot), with the desktop's Lucide icons in `assets/icons`.

The packaged worker is for the reviewed built-in only. A separate process is **not an OS sandbox** and must not be used to run arbitrary installed plugins. No HTML, Tauri, Wry or webview is used by this native UI; a plugin page is React rendered by `wings-plugin-ui/native` into a tree of data, never into a DOM. Memory, measured once on macOS with the same 36 panes and saved output as a desktop workspace, at the same window size: about 180 MB for the native app, about 1.3 GB for the desktop app and its WebKit processes. With all 36 panes full, the native app uses about 870 MB, and about 200 MB once the hidden panes have unloaded.

The default `ui` feature enables the optional GPUI and terminal dependencies. The library and worker build with `--no-default-features` without GPU dependencies. Keep `wings-native` and `wings-plugin-worker` together in the same executable directory. The `theme` module mirrors the existing desktop palette.

Plugin pages in React (a pilot, not yet in the window): `pages/pilot.tsx` uses `wings-plugin-ui/native`'s `Page`, `Toolbar`, `Button`, `Badge` and hooks, and `node apps/native/pages/build.mjs` bundles it with React and the page renderer into `pages/dist/pilot.js` (`--check` fails when that file is stale). `src/page/runtime.rs` runs a bundle in QuickJS on its own thread: the page sees only `wings.render(json)` and real `setTimeout`/`clearTimeout`, and a turn that runs over a second ends the page. `src/page/tree.rs` checks each tree the page sends (unknown components are dropped, sizes bounded), and `PageView` draws it with `src/ui` and sends a click back to the page's handler by id, which renders again.

A plugin's main script and its pages run side by side: `PluginHost` (`src/page/plugin.rs`) starts the main bundle and any number of pages, each in its own QuickJS thread with the same budgets, so a frame that throws or never stops ends alone. Its frames talk with `wings.broadcast` and `wings.onBroadcast` as the desktop's do (JSON of at most 64,000 characters, to every other frame of the same plugin and nobody else, in order; `wings-plugin-sdk/messages` splits anything bigger) and share `wings.storage`, which is the desktop's `wings-plugin-storage` under the plugin's id and install scope, which the app passes as `PluginConfig`'s storage root and scope. A frame also gets `setInterval`, a `console` that discards its output, and `wings.focused` and `wings.onFocus`, which only say the window is focused. A frame of a plugin whose host has the plugin's manifest (`PluginHost::with_access`, which the window uses) also has `wings.onPanes`, `setBadge`, `setPaneStatus` and `onAction`, `exec`, `openUrl`, `ports`, `notify`, `transcript`, `onTranscript` and `statusline`, written as `apps/desktop/public/plugin-sdk.js` writes them and answered as the desktop's `handle` and `plugin_*` commands answer them (`src/page/plugin/calls.rs`): the permission is `wings-plugins`' to give (`permissions`, `exec`, `fetch::may_open_url`, `transcript`), with the desktop's argument rules and messages. A call that reads the disk or runs a program runs on a thread of its own and answers the frame's promise when it is done, so it never holds up the frame. `disks`, `diskFind` and `diskUsage` use the desktop's `wings-disk-usage` crate: a scan reports its progress while it runs, and stops when its frame ends or its `signal` aborts. Disk usage runs on them: its map is plugin-ui native's `Sunburst`, which the app draws from the wedges the page lays out (no zoom between folders, no dragging a wedge to the Collector, no keyboard shortcuts, and the list shows its biggest 120 rows with a button for more), beside a `Scroll` list in a `Split`. `statusline` has what Claude Code last told `wings statusline` (see Claude Code below), and `notify` ignores `actions`. A plugin's main also answers the tools other plugins call (`onTool`, and `callTool` between Wings' own plugins, with the desktop's checks), `closeView` closes a page wherever it shows in the project on screen, and `project` is the project on screen. `createWorktree`, `worktreeSetup` and `setWorktreeSetup` work on the app's own project list, with the desktop's checks and code (`crates/wings-spaces`): a worktree is made beside its repo, listed under its project in the sidebar, and its project's setup line is typed into the first pane a plugin opens there. `claudeAccounts` and `setClaudeAccount` list the Claude Code accounts and set the one each project uses, with the desktop's checks and code (`crates/wings-spaces`): a new terminal in a project starts with that account's `CLAUDE_CONFIG_DIR`, and `transcript`, `onTranscript` and agent detection read every account's folder. Settings, Agents connects Claude Code in that account too. `setProjectSection` refuses, since the app has no project sections to show. `fetch`, `secrets` and `post` are the desktop's (`src/page/plugin/calls/pr_tracker.rs`; `wings-plugins` checks the URL, headers, bearer and path; a request is `ureq`'s with no redirects and a 30 s limit), with the secrets in the system keychain under the desktop's service name, so a token saved in either app is there for both. The names a plugin stored are noted in `plugins.json`, as the desktop notes them, so removing the plugin deletes them. `sendToAgent` pastes the message, with the desktop's header and its checks, into the prompt of the agent in a pane, refuses one where you typed and haven't sent it, and presses Enter a moment later only while Settings, Agents' "Let agents message each other" is on, answering `{ submitted }`. It doesn't know whether you have typed into the prompt, which the desktop also refuses over. `openSettings` shows the plugin's settings page (`contributes.settings`, built to `dist/native/settings.js`) in a window of its own, not in Settings. `emit` and `onEvent` send an event from one of Wings' own plugins to the main of those that declared it. `onReply` is accepted and never called, since the native diff viewer has no reply box. `viewArgs` is what `openView` passed as `args` (only for a tab, up to 16 KB): a view that is open takes new args by starting over, a `multiple` view opens a tab unless one has the same args, and a tab's args are saved with it. The rest of the desktop's `wings` API (opening panes and views, diffs) isn't here until a native plugin needs it. `pages/fixture/` is a plugin written like the real ones, with `channel` and `useQuery`: `node apps/native/pages/build.mjs` builds `pages/<name>.tsx` and each plugin folder's `main.ts` and `page.tsx` (and `<name>-page.ts`) into `pages/dist/`.

The window runs the desktop's plugins (`src/installed.rs`). It owns the desktop's data folder (`dev.wings.app`) as the desktop does: `wings-plugins`, the desktop's own crate, loads the folders in `plugins/` with the desktop's rules, and `plugins.json` says which are turned on and whether their permissions are approved, so a plugin runs here exactly when it runs there. A plugin with a native build (`dist/native/main.js`, which the plugin build writes for a manifest with `"native": true`) has its main started in a `PluginHost` with the desktop's `plugin-storage/` folder and the install scope `plugins.json` names, so what it saves is shared with the desktop (a plugin installed here gets its scope when it is installed, as on the desktop). A plugin without that file isn't ported and is skipped without a message, and so are plugins the desktop skips. Settings, Plugins installs from a GitHub link (a repo, its release's `.wings-plugin`, or a plugin folder in a repo) or a `.wings-plugin` file, shows what each plugin may access, asks with "Turn on <plugin>?" before one runs and again when an update asks for more, turns plugins on and off, checks GitHub for newer versions, updates, reinstalls and removes, all through `wings-plugins`' `Store` with the desktop's checks (`src/workspace/plugin_manage.rs`); `wings plugin install|link|update|enable|disable|remove` does the same over the socket. A change starts or stops the plugin's main and pages at once. A plugin on without a native build shows "On · No native build". Not here: the desktop's Available list of the Wings repo's plugins, its periodic update check and toast, dropping a file on the window, the README and the "needs" tool installs on a plugin's page. `minWingsVersion` is checked against the desktop's version, which `build.rs` reads from `apps/desktop/src-tauri/Cargo.toml` (this crate's own `0.1.0` would be wrong, and a constant would need an edit with every desktop release). A view that opens as a tab, sets `newTab` (what the desktop's + menu lists) and has a native page `dist/native/<page>.js`, for the page file the manifest names (`dist/board.html` is `board.js`), is listed under Plugins in the sidebar. A click opens it as a tab after the terminals, named after the view and running a frame of its plugin until the tab closes (Cmd-W or its X), once per view and project unless the view sets `multiple`. Switching projects keeps each project's pages running, Cmd-] and Cmd-1..9 reach them, Move Tab swaps them among themselves, and the open pages are saved with the tabs and come back on the next launch unless their plugin has been turned off. A plugin's sidebars (`contributes.sidebars`, built to `dist/native/<page>.js` like a view's page) get a title bar button each, at the right end, which opens the page in a panel on the right (360 points, at most 40% of the window, not resizable yet); the page keeps running while the panel is closed, and a click on a status strip that names the sidebar opens it. Plugins draw on panes as the desktop's do: a `badges` plugin's pill in the pane header opens a card with its rows and buttons, and a click on a button is the main frame's `onAction` (the button waits for it, and shows the error it throws), and a `status` plugin's strip under the terminal shows its items, with the rows in a card on hover. A notification goes through `osascript` on macOS (`notify-send` elsewhere), which needs no app bundle; where that fails it is shown in the window instead. The panes are told to plugins as the window draws, when something about them changed (about 4 µs on a quiet frame with 20 panes in an optimized build). Transcript entries come from following the transcripts of the Claude sessions found in panes (`src/transcripts.rs`, the desktop's tailer ported), only while a running plugin may read transcripts. `wings.ports` is the desktop's lookup ported (`src/ports.rs`). `wings.agentActivity` asks OpenCode's background service as the desktop does (`wings_agents::agent_activity`, moved out of the desktop so both use it), and `wings.onAgentActivity` hears which OpenCode session did something, one event per burst of calls, only while a running plugin may read agent activity. A debug build takes `--plugins-dev-root PATH` to run the plugins of a folder as well, as the desktop's debug builds run the repo's `plugins/`: `cargo run --manifest-path apps/native/Cargo.toml -- --plugins-dev-root plugins` runs dev-servers and HUD from the repo, always on and approved, a plugin the desktop has no record of storing what it saves under the scope `dev`. `cargo run --example shot_plugins --features test-support -- <out-dir>` renders a badge, its card, a strip and a sidebar offscreen, and with `--changes`, `--schedules`, `--pr-tracker`, `--session-detail` or `--disk` those plugins' pages over made-up data. Not done yet: the + menu and project sections the desktop also lists pages in, a `noProject` view, and picking up a plugin the desktop app installs or turns on while this app runs. `Config.plugins` holds the folder, state file and storage root, as `projects` and `state` hold theirs; tests and the `shot` example point them at temp folders.

Claude Code connects to this app exactly as it connects to the desktop's, so swapping the apps changes nothing in its config (`crates/wings-connect`, which both apps use). `cargo build --bins` also builds `wings`, the desktop's `wings` command, which the bundle carries beside `wings-native` (`scripts/install-mac-app.sh`): `wings --mcp <socket>` is Claude Code's MCP server, `wings statusline` is chained in front of your status line, `wings hook` runs after your SessionStart, PreToolUse (Bash) and UserPromptSubmit hooks, `wings journal` is the change journal's sink, and `wings plugin`, `wings tools`, `wings <plugin> <tool>`, `wings wait` and `wings worktree-setup` are the CLI. All of them talk to the running app over the desktop's socket, `mcp.sock` in the desktop's data folder (`dev.wings.app`); the app keeps its own state in `Wings Native/`. On start the app serves that socket as the desktop does, replacing one an earlier run left, and a release build of the installed app connects Claude Code to its own `wings`, in the default account and each account a project uses, unless you disconnected it (`Wings Native/claude-disconnected`): the MCP server is registered with `claude mcp add` at user scope, and the status line and hooks are chained with yours and put back byte for byte on Disconnect. Settings, Agents shows each account's state and has Connect, Reconnect, Disconnect and "Load Wings tools at session start". The socket answers Wings' own tools (`search_history`, `read_session`, `list_sessions`, `read_pane`, `open_pane`, `close_pane`, `send_to_agent`, `notify`, `worktree_setup`, `project_info_*`) against this window's panes, agents and projects, and the tools of the plugins that run here; a hook goes to the `wings.onHook` of the running plugins that declare it, and a status line to `wings.statusline()`. `open_pane` presses Enter after the command only while "Let Claude run commands in new tabs" is on, and `send_to_agent` only while "Let agents message each other" is on (both in Settings, Agents, off by default as on the desktop). `worktree_setup` with a new setup command asks you with "Allow this setup command?" and saves nothing until you allow it, one prompt per project at a time, with Allow armed after a second. Not yet: `close_pane` closes only panes of the project on screen, and OpenCode isn't connected from here. `Config.socket` is set only by `main`, so tests and screenshots never take the socket of the Wings you use or touch Claude Code's settings.
