# One-click CLI sign-in for Wings plugins

Don't write the sign-in handling by hand. `cli::Cli` of the `wings-plugin` crate (`packages/plugin-rs/src/cli.rs`) runs `az`, `gh` or `glab`, tells "not installed" and "signed out" from a failed call, remembers the problem, builds the badge with Install, Sign in and Try again, and runs the login. The plugin gives it two things: how to see from stderr that the CLI is signed out, and the login's arguments. The doc comments in `cli.rs` say what every call does. For the plugin API itself, see the `wings-plugin` skill and `plugins/README.md`.

Examples in this repo:

- `plugins/work-item/rust/src/az.rs` makes the handle, and `plugins/work-item/rust/src/main_frame.rs` (`badge_of`, `watch_cli`, `act`) draws the badge and answers its actions.
- `plugins/pr-tracker/rust/src/track/badges.rs` (`problem_badge`) does the same for three CLIs with a tone each, and `track/retry.rs` (`connect_clis`, `sign_in`) signs in, installs and tries again.
- `plugins/pr-tracker/rust/src/forges/` has a handle per host: `github.rs` for a login that prints a one-time code (`sign_in_args` hears each line it prints), `gitlab.rs` for a signed-out signal that needs a second command, and `azure.rs`.

## Steps

1. **Find the logged-out signal.** Reproduce it without signing the user out by pointing the CLI at an empty config folder in the scratchpad. For example, `GH_CONFIG_DIR=<empty dir> gh pr list` exits 4 and prints `To get started with GitHub CLI, please run:  gh auth login`. `az` prints a message that mentions `login`. `glab api` prints `401 Unauthorized`, but a private project answers `404` when you're signed out, so check `glab auth status --hostname <host>` on a 404. Match on stderr, because exit codes alone are shared with other failures.
2. **Make the handle.** `Cli::new(program, name, signed_out, sign_in)` in a `thread_local!` static (a frame is single-threaded, and `Cli` is an `Rc`). `name` is what Install says ("Azure CLI"). `signed_out` is a `fn(&str) -> bool` of stderr, like `|stderr| stderr.to_lowercase().contains("login")` for `az` (`work-item/rust/src/az.rs`). `sign_in` is the login's arguments as a `&'static [&'static str]`. A login that depends on the host (`--hostname`) takes `&[]` here and is run with `sign_in_args(key, &args, on_line)` instead. When stderr can't tell (glab's 404), `signed_out` stays strict and the plugin calls `record_signed_out(key, message)` after its own second check (`forges/gitlab.rs`).
3. **Call the CLI through it.** `run(&args, key, quiet)` gives stdout, `json(&args, key, quiet, empty)` parses it (`empty` is what a program that prints nothing means; `None` makes that an error), `run_in` and `json_in` take a `cwd` first, and `exec` gives `Exec { code, stdout, stderr }` whatever the exit code and records no sign-in problem. They fail with a `CliError` whose `kind` is `Missing`, `SignedOut` or `Failed`, and whose `message` is all of stderr (`last_line` cuts it to one line for a badge). `key` is what a problem is recorded under: the Azure organization, or a provider and host. A working call clears the problem. Pass `quiet: true` for a background read that must not turn badges into sign-in prompts. `problem(key)` reads what is recorded, for a plugin's own badges.
4. **Show the button.** `problem_badge(key, &ProblemText { title, signed_out, missing })` gives the badge for a pane while the key has a problem, or `None`. It replaces the pane's badge, even a PR badge, because nothing works until sign-in. Its actions have the ids `install` (with `missing`), `signin` (primary) and `retry`, and its tone is `warning`. A plugin with several providers sets `badge["tone"]` itself so the user can tell them apart (`track/badges.rs`: `info.tone`; GitHub is `merged`, GitLab is `info`, Azure DevOps is `warning`). Give a new provider a different one. In the action handler, answer the ids with `cli.install().await`, `cli.sign_in(Some(key)).await` and `cli.retry().await`, and return the future's result so the button spins (`work-item/rust/src/main_frame.rs` `act`).
5. **Redraw and reload.** `on_change(listener)` is called when a problem is recorded, changes or goes, or a sign-in starts or ends: draw the badges again there. `on_retry(listener)` is called by Try again and after a sign-in: clear the caches of what failed for lack of the CLI and load it again, and return a future. Connect both once at startup (`watch_cli`, `connect_clis`).
6. **Read the CLI's login code before calling it.** Wings runs programs with no TTY and stdin closed, and many CLIs change behaviour without a TTY:
   - `gh auth login --web --clipboard --hostname github.com` doesn't open the browser without a TTY. It prints `One-time code (XXXX-XXXX) copied to clipboard` (or `First copy your one-time code: XXXX-XXXX`) and `Open this URL to continue in your web browser: <url>`, then waits. Source: `internal/authflow/flow.go` in cli/cli v2.102.0. `Cli::sign_in_with(key, on_line)` and `sign_in_args` get each line it prints: put the code in the badge label and call the host's open-URL with the URL (`plugins/pr-tracker/rust/src/forges/github.rs` does). The URL's prefix must be in the manifest's `openUrl`.
   - `glab auth login --web --hostname <host>` goes straight to the browser OAuth flow without a TTY and opens the browser itself (`internal/commands/auth/login/login.go:587` in glab v1.121.0). A self-managed server needs an OAuth app ID first (`glab config set client_id`), and glab says so in its error.
   - `az login --allow-no-subscriptions --output none` opens the browser itself. Its subscription picker only appears with a TTY (`can_show_selector` in `azure/cli/command_modules/profile/custom.py`). `--allow-no-subscriptions` lets accounts that only use Azure DevOps sign in.
7. **List the commands.** Every program and subcommand `Cli` runs, the login included (`az login`, `gh auth login`), has to be in `permissions.exec` of `wings-plugin.json`, since the user approves that list (see `plugins/work-item/wings-plugin.json`). A sign-in waits up to 5 minutes and then retries, and the host waits for an action up to 310 s, so the button spins for the whole sign-in.
8. **Never touch tokens.** The plugin doesn't read, store or pass credentials. The CLI keeps its own.

## Check it

- Test with the SDK's `host::testing::answer`, which hands the `Cli` a fake `exec` answer: give it the empty-config stderr from step 1, run a call, and check that `problem(key)` is recorded and `problem_badge` returns the badge. `cli.rs`'s own tests and `plugins/work-item/rust/src/main_frame.rs` (the `signin` and `retry` cases) show the shape. Run the plugin's tests with `cargo test --manifest-path plugins/<id>/rust/Cargo.toml`.
- Build the frames as the `wings-plugin` skill says and look at the badge with the empty config folder in the environment. The first call should set the Sign in badge.
- The real browser sign-in needs the user's account. Ask them to click Sign in and tell you what the badge shows.
